# Parley Design — Execution Scope & CLI

> **Scope:** `ProcessRunner`, `ExecutionScope`, `ExecutionError`, `ManifestFile`, `CLI`, `CliResult` — the Phase 3 closer (Sprint 6) — plus `CommandLine` and the diagnosis boundary (Sprint 8) and `LockError` (Sprint 9). All classes in the `Parley` namespace, all in `src/exec/`; structural immutability applies throughout (class-side construction; zero public setters). This document is where Parley finally touches the operating system: it defines the ONE process seam, the curated child `gst` invocation, the resolution of the deferred `gst Package.st` caveat (§8 decision 19), and the command-line verbs wired over Sprints 0–5. Every 3.2.5 mechanic pinned here was verified empirically against the toolchain at staging (issue #8).

---

## 1. `ProcessRunner` (the one process seam)

The **only** pathway in all of Parley by which a child process is ever created. Everything above it composes command lines as pure string values; everything at it is one thin, dumb executor.

- `ProcessRunner class >> new` — stateless; exists as an instance so tests can substitute a recording/failing double.
- `run: aCommandString` — executes the command via the 3.2.5 kernel's `Smalltalk system:` and answers the child's **exit code** as an Integer. 3.2.5's `system:` answers the raw wait status (exit code × 256); `run:` normalizes it: `status // 256`. `0` is success; nothing is signaled — the code is an answer, and its meaning belongs to the caller.
- No output capture in MVP: the child's stdout/stderr flow to Parley's own (the CLI is a terminal program). No shell-quoting layer: Parley composes its own command lines from paths it controls.

## 2. `ExecutionScope` (the curated child image)

The honest `bundle exec` for 3.2.5 (§8 decision 16), and the single home of invocation logic. A scope holds three collaborators immutably:

- `ExecutionScope class >> on: anInstalledSet target: aTargetDir runner: aProcessRunner`.

### 2.1 Registration (executing Sprint 5's plan)

- `registrationCommands` — exactly `anInstalledSet registrationCommandsFor: aTargetDir` (the Doc D §4 plan; a pure value).
- `register` — runs each plan line, in the plan's order (sorted package-name order, each package's staging line immediately before its registration line — Doc D §4), through the runner. The first nonzero exit signals one **`ExecutionError`** naming the exact command line and the exit code; later commands are not attempted. **Fail-stop, not batched:** an execution failure is environmental (a broken toolchain, an unwritable disk, a corrupt archive rejected by `gst-package`), unlike install problems, which are per-package data problems — retrying the rest teaches nothing and can half-register an environment. Empirical anchor (issue #8 ruling): 3.2.5's `gst-package` validates the archive (a `.star` is a zip) and exits `1` on a non-archive file (`gst-package: Invalid argument`) — the staging line copies any bytes, so garbage fails precisely on the registration line. Note the flagless mode: 3.2.5's option parser accepts **no** `--install` spelling; install is the default mode, and the `--help` text claiming the flag is stale upstream.
- Registration is (re-)runnable: the staging copy and `gst-package --target-directory` both overwrite identical files harmlessly (verified). Switching or rolling back an environment re-points at a different target — it never mutates one. The `.parley-staging/` directory the plan writes under the target is invisible to the child (`PackageLoader` scans the image directory for `*.star` files only) and is left in place — target-confined residue, not state.

### 2.2 The child invocation

- `childCommandFor: aScriptPath` — the pinned composition, exact:

  ```
  gst -i -I <aTargetDir>/parley.im --no-user-files <aScriptPath>
  ```

  Why each element (verified against 3.2.5; corrected by the issue #8 ruling): `-I <target>/parley.im` places the image in the target directory, and 3.2.5's `PackageLoader` local package registry follows the image directory — every `.star` sitting there is visible to the child **by its filename**: `Kernel.StarPackage` requires the `package.xml` name to equal the filename basename (`kernel/PkgLoader.st`), so a package is loadable iff `<target>/<InternalName>.star` exists. This is why Doc D §4's plan registers each archive under its true name — a content-addressed `<sha256>.star` is invisible to the child. `--no-user-files` excludes `~/.st` customizations. `-i` rebuilds the image from the kernel every run: no state leaks between runs, and the scope needs no image lifecycle management. The platform's system packages remain visible to the child — they are the host runtime, as a language's standard library is under any `bundle exec`.

- `run: aScriptPath` — `runner run: (childCommandFor: aScriptPath)`, answering the child's exit code. A nonzero child is the script's own business — an answer, never an `ExecutionError`.

## 3. `ManifestFile` (decision 19 resolved)

`ManifestFile class >> load: aPath` reads the developer's **own** `Package.st` and answers its `LibraryManifest`:

0. **check the path first** (Sprint 8): if `aPath` does not exist or is not readable, signal a one-problem `ManifestError` naming the path and the verb that writes one (exact wording pinned in RED). This is the sprint's **third declared settled-class exception**, granted at the Sprint 8 RED review. It exists because 3.2.5's `FileStream fileIn:` signals `SystemExceptions.FileError` — a *kernel* error — on a missing file, so without this check the most ordinary user error in the tool (`resolve` before `parley init`) reaches §4.2's boundary as an **undiagnosed** error and is answered with exit `70`: *"this is a defect in Parley, not in your project."* That is the fail-wrong disease in its second form — not a lying exit code, but a lying attribution of blame. A missing `Package.st` is the operator's problem and Parley must say so: exit `1`, one problem, naming the fix.
1. clear the recorded manifest;
2. file the path in with `Namespace current: Parley` — inside the namespace the token `Parley` resolves to the `Parley.Parley` gateway (§8 decision 19), so the Doc B §2 syntax works verbatim;
3. answer the authoring error the file-in captured, if any (below); then the manifest recorded by `define:`; if the file recorded nothing (no `define:` reached), signal a one-problem `ManifestError`-style error naming the path (exact wording pinned in RED).

**The authoring-error boundary** (Sprint 9, closing half of the decision-32 gap): an author error inside the developer's own `Package.st` — a selector outside the manifest vocabulary (`ManifestVocabularyError`), or a declaration that fails validation (`ManifestError` from `ManifestBuilder>>build`) — is answered as the author's diagnosis at exit `1`, carrying the original error's own text unchanged. The errors already *read* as diagnoses (`Package.st sent #nmae - not part of the manifest vocabulary. Did you mean #name?`); what was wrong was who they blamed. Nothing about the message changes — only its classification.

**Where the boundary can live (verified against 3.2.5, Sprint 9 RED review).** It is *not* an `on:do:` around the file-in, and the earlier text of this section saying "the file-in of step 2 is wrapped" was factually wrong. The doit context of a filed-in statement is **parentless** — `thisContext parentContext` from inside a filed-in file answers `UndefinedObject>>__terminate`, not the caller of `fileIn:` — so a handler around `FileStream fileIn:` is not in the signaling chain and never fires. gst prints its own backtrace, abandons the statement, and `load:` then answers the *wrong* diagnosis ("no manifest defined" about a file that did send `define:`). `Behavior>>evaluate:` was probed as an alternative and fails identically. Only a handler in a method frame **called by** the filed-in statement catches the error, with the message intact and the file-in continuing.

The boundary therefore lives in `Parley.Parley class >> define:` — the one Parley frame a filed-in `Package.st` enters. This is the sprint's **third declared settled-class exception**, granted at the Sprint 9 RED review: `define:` wraps the builder construction, the author block's evaluation and `build` in one `on: ManifestVocabularyError, ManifestError do:` handler, which hands the error to `ManifestFile` (where all recording state already lives) and returns `nil`. `ManifestFile load:` then signals from **its own** frame, where the handler is real:

- a captured `ManifestVocabularyError` ⇒ one `ManifestError` problem carrying the vocabulary error's message text verbatim, suggestion included;
- a captured `ManifestError` ⇒ re-signaled with its `problems` **intact**, never flattened to one line — the batch report is the whole point of `ManifestError` (Doc B §3.3: an author fixes a `Package.st` per edit-run cycle, not per error).

Two ordering rules make this sound, and both are load-bearing: `load:` clears the captured-error slot alongside `recorded` at entry, so no stale error leaks from a previous load; and it checks the captured error **before** the `recorded isNil` check, or the lying "no manifest defined" diagnosis survives. Where a file sends `define:` more than once, the **first** authoring error wins and is reported even if a later `define:` succeeds — a `Package.st` with a broken `define:` must never half-succeed.

**The capture is scoped to a load in progress, and that scoping is part of the design — not an implementation detail.** `define:` is not only the file-in path: it is also the settled live API, and a `Parley define:` evaluated in an image or a test must signal to *its own caller*, which is exactly what the Sprint 1 laws encode. Capturing unconditionally would swallow those signals and silently break that contract. So the boundary asks `ManifestFile isLoading` and captures only when the answer is yes — the one context whose signaling chain is cut; everywhere else it sends `pass` and the error travels untouched. The flag is set around the file-in and cleared in the **`ensure:`**, so a load that fails part-way can never leave the image in a state where live authoring errors vanish. (Found in Sprint 9 GREEN: the ruling as first written said only "`define:` wraps … and hands the error to `ManifestFile`", and taken literally it broke five settled Sprint 1 laws. Written down here so nobody implements the hole again.)

Both classes are therefore never signaled out of a verb, and the §4.2 closed set can say so without qualification.

Sprint 6's exception stands unchanged alongside it: `define:` sends `ManifestFile record: manifest` before answering. All recording state (the holder, the clear, the read, and now the captured authoring error) lives in `ManifestFile`; no domain decision moves into the gateway.

**Trust boundary unchanged** (architecture §2.2): only the root application's own manifest is ever loaded this way — the file its author owns and runs. Third-party `Package.st` files are never evaluated by anything (their information enters only as static index entries through the literals-only reader); the hard bans still hold — file-in of the owner's manifest is the authoring path Doc B §2 always specified, and no third-party byte ever reaches it.

## 4. `CLI` and `CliResult`

- `CLI class >> in: aWorkingDir source: aPackageSource store: aContentStore target: aTargetDir runner: aProcessRunner` — every collaborator injected (`source` may be `nil` for verbs that need none); tests pass doubles, the executable wrapper passes the real ones. The CLI reads `Package.st` and `parley.lock` in `aWorkingDir`.
- `run: anArgvArray` — dispatches the verb and answers a **`CliResult`**: an immutable value carrying `lines` (Array of Strings — everything the wrapper should print) and `exitCode` (Integer). The CLI **never** prints, never terminates the image, and never touches a process except through the scope's runner: it is an orchestration answering a value. Argv grammar: `init` | `resolve` | `install` | `update [<pkg>]` | `add <pkg> <constraint>` | `exec <script>` | `publish <dir>` | `why <pkg>` | `tree` | `check`. An unknown verb, a missing `exec` script, **wrong arity** (`update` takes at most one package), or a source-requiring verb with no source answers the pinned usage lines with exit code `2` — and the `verbs:` line renders the optional argument exactly as this grammar spells it, `update [<pkg>]`. **The usage lines name the source flags**, not only the verbs: `--source`/`--git` are how the most common verbs reach an index, and a usage message that lists `resolve` while hiding what `resolve` needs leaves the operator exactly as stuck as no message at all.

### 4.1 Verbs

- **`init`** — writes a **starter skeleton** `Package.st` in the working directory; refuses (one line, exit `1`) if the file exists. The skeleton is deliberately **not** Doc B §2's illustration. That example declares `kernel-json` with two dependencies that exist nowhere, so `init` followed immediately by `resolve` failed on phantom packages — the worst possible first run, and unnoticed because the round-trip law asserted the *illustration's values* rather than the *template's fitness*. A template's job is to be a correct starting point, not a feature tour; the dependency syntax is taught in the skeleton's header comment, where it costs nothing to read and nothing to resolve. Two laws now split the claim: Doc B §2's syntax still round-trips through `load:`, **and** what `init` writes loads and declares no dependency the operator does not have.
- **`resolve`** — `ManifestFile load:` → `source snapshot` → `Resolver`. A `Resolution` is written to `parley.lock` via the settled `IndexEntryWriter writeLock:on:` (byte-stable) and reported, exit `0`: one `<name> <version>` line per pin, or — when the project declares **no dependencies** — one pinned confirmation line. Zero pins used to mean zero lines, so a successful `resolve` printed nothing at all and read as a verb that had done nothing, on exactly the first run after `init`. Silence is the wrong report for success. A `ConflictReport` answers its narration lines, exit `1` — a conflict is a value, never an exception.
- **`install`** — the lockfile fast path, then the Sprint 5 pipeline, then registration:
  1. **Pin fast path:** if `parley.lock` exists, read it (settled reader), rebuild the `Resolution` (`fromLockEntry:`), and check `PinVerification of: manifest lock: resolution`. **The read is a boundary** (Sprint 9): a lockfile that does not parse, or parses but is not a `#'parley-lock' 1` artifact, signals one **`LockError`** naming the lock path and the reader's own message (wording pinned in RED) — never a raw `IndexEntryParseError`/`IndexEntryFormatError`, which is how a corrupt lock used to reach the §4.2 boundary undiagnosed and be answered with exit `70`. The diagnosis names **`parley update`** as the repair, because `update` is the one verb that ignores the lock entirely and rewrites it — the same shape as `init` in the missing-`Package.st` diagnosis (§8 decision 31). A corrupt lock is the operator's file, not Parley's defect.

     **Readability is checked before shape** (§8 decision 56, Sprint 16). The boundary above validates what the file *says*; it presumed the path could be read at all. `File>>exists` answers `true` for a **directory**, and `File>>contents` on one signals a kernel `SystemExceptions.WrongClass` that escapes the handler above — so a `parley.lock` that is a directory (a botched checkout, a volume mount, a stray `mkdir`) reached §4.2 as `internal error: WrongClass: Invalid argument -9223372036854771711: must be a SmallInteger - this is a defect in Parley, not in your project`: exit `70`, a kernel integer on screen, and the file never named. So the boundary now begins by requiring the lock path to be a **regular readable file**, answering one `LockError` naming it in the same three-part shape (path, defect, `parley update`) when it is not. **The settled corrupt-lock behaviour is unchanged and is the line that separates the two cases:** a lock that is *readable but malformed* is still ignored by `resolve`, which stays exit `0` (§4.1), because `resolve` is about to overwrite it. A lock that cannot be read as a file at all is refused by **every** verb including `resolve`, because the write that would fix it cannot succeed either — and answering `0` while being unable to produce a lock is the fail-wrong this whole boundary exists to prevent.

**The third rejection ground — body-shape validation (Sprint 10, closing §8 decision 35).** The two grounds above are *syntactic*. A lockfile that parses, carries `#'parley-lock'` and declares a supported format version but has a **malformed body** — a missing `#packages` key, say — passed both and reached `Resolution fromLockEntry:`, where it died as a *kernel* `SystemExceptions.NotFound` and was answered with exit `70`: "this is a defect in Parley, not in your project." The same sentence, on the same file, that this section exists to abolish, one hand-edit away. The §4.2 closed-set law was structurally blind to it, because that law enumerates **`Parley` error classes** and this one is the kernel's.

So after the tag and format-version checks, and **before** `Resolution fromLockEntry:` sees the value, the parsed structure must have the Doc B §5.3 shape:

- the two keys `#root #packages`, present, **in that fixed order** (§5.4 rule 2), `#root` a String;
- `#packages` an Array, each element a **four-element** `#(<name> <version> #sha256 <hex>)` — name and version Strings, the literal symbol `#sha256` in third position, the digest a String;
- each `#version` must **parse** as a `Version` through the settled `Version fromString:` — the Doc F §4.1 lesson, that a shape check never asks whether the string means anything;
- each `#sha256` must be **64 lowercase hex characters, or `''`** (Sprint 11, §8 decision 42; Doc B §5.3) — the shape a digest renders as, or the writer's own rendering of a pin with no published archive. Shape only: whether a digest matches its bytes stays `verifyHash:`.

A violation is one `LockError` problem naming the lock path, the defect, and `parley update` (wordings pinned in RED) — the same three-part shape the syntactic grounds already use. **One problem per lockfile**, first defect found: the operator is repairing one file, not auditing it, and the repair is the same regardless. Where a lock offends two value grounds at once, **every version is checked before any digest is**: the version wording is the older pinned answer, and a ground added later must not shadow one already settled. The settled `Version fromString:` is *consumed*, never re-implemented — it stays the single definition of what parses (Doc F §4.1).

`Resolution fromLockEntry:` is unchanged and stays trusting: it is fed only values this boundary has already accepted, exactly as `LibraryManifest fromIndexEntry:` is fed only entries the scan validated. Valid ⇒ that resolution is used **without consuming the source's snapshot** (mechanically provable: a snapshot-signaling source double). Invalid or absent ⇒ resolve fresh and rewrite the lock.
  2. **Hash-vs-cache:** for every pinned sha256 the store contains, `verifyHash:` must answer `true`. A tampered entry is a **fail-stop corruption report** naming the hash (exact wording pinned in RED), exit `1` — the store never repairs itself (Doc D §3: detection only; repair is an operator action).
  3. **Install:** `Installer install:` (cache hits skip fetch; an `InstallError`'s problems become the lines, exit `1`).
  4. **Register:** `ExecutionScope register` over the installed set (an `ExecutionError`'s message becomes the lines, exit `1`). Exit `0` on success.
- **`update`** — ignores any existing lock: resolve fresh, rewrite `parley.lock`, then install + register as above. (`install` keeps a valid pin; `update` is the verb that moves it.)
- **`update <pkg>`** (Sprint 12) — moves **one** package and leaves the rest of the lock where it is. The all-or-nothing grammar above is the honest MVP default and the wrong tool for the commonest real request: *take the patch release of this one dependency, change nothing else.* Today the only answer is `update`, which moves everything and hands the operator a diff they did not ask for and must review anyway.

  It resolves the ordinary way against a **narrowed snapshot** (Doc C §2.2): every *other* pinned package is held at its locked version, the named one is free to move, and whatever the named one drags with it moves too. The `Resolver` is untouched — a selective update is a normal resolution of a smaller world. On success the lock is rewritten byte-stably and `install` + `register` run exactly as `update` does; pins that did not move are byte-identical, which is the property that makes the diff reviewable and is worth a law of its own.

  Its diagnoses, all exit `1` and none of them exit `70`:

  - **no lock** — the same line the inspection verbs answer (`parley.lock is missing - run parley resolve to write it`). There is nothing to hold selectively when nothing is pinned.
  - **`<pkg>` is not pinned** — one line naming it, the `why` precedent: the operator asked about a package they do not have.
  - **held pins make it unmovable** — the settled `ConflictReport` narration, **preceded by one line** naming that the other pins were held and that `parley update` moves everything. The resolver answers truthfully about a world with few candidates but cannot know *why* the world was small; the verb had that context and owes the sentence (Doc C §2.2).

  When the named package is already at the newest version its constraints allow, that is a **success with a line saying so**, exit `0`, and the lock is rewritten to identical bytes — the `resolve`-with-no-dependencies precedent: a verb that prints nothing reads as a verb that did nothing. **Install and register still run** (ruled at the Sprint 12 close-out, §8 decision 48): already-newest changes what the verb *reports*, never what it *does*. The pins are unchanged, but nothing guarantees the store and the target directory still hold them — a cleared store or a fresh checkout is the ordinary case — and a verb that skipped the pipeline would answer `0` while registering nothing. `install` is idempotent, so running it unconditionally costs a cache-hit pass and keeps the verb's one contract whole.
- **`add <pkg> <constraint>`** (Sprint 13) — declares a new dependency in `Package.st` and moves the project to it in one operation. The edit is a **textual insertion into a recognized cascade, verified by re-loading through `ManifestFile load:`, and rolled back on any refusal** — the mechanism and its reasoning are Doc B §2.1, and the short version is that `Package.st` is executable Smalltalk the author owns, so Parley never re-renders it.

  After the edit it resolves against a snapshot narrowed to **hold every existing pin** (Doc C §2.2 — the third application of the trick, after retirement and selective `update`): adding a dependency should not silently move the ones already there, for the same reason `update <pkg>` does not. Then the lock is rewritten byte-stably and `install` + `register` run exactly as `update` does.

  **`add` is atomic** (Doc B §2.1): the manifest and the lock move together, or neither moves. Every diagnosis below restores the original `Package.st` byte-for-byte and leaves the lock as it stood. A fetched archive may remain in the content-addressed store, inert until a lock pins it — Doc B §2.1 states why that is outside the claim rather than an exception to it.

  Its diagnoses, all exit `1` and none of them exit `70`:

  - **no `Package.st`** — the settled missing-manifest line naming `parley init` (§8 decision 31); there is nothing to add to.
  - **a shape `add` cannot recognize** — one line naming the exact `dependency:constraint:` text to paste and the file, because a refusal that does not say what to type is a refusal that wastes the operator's time.
  - **already declared, with a different constraint** — one line naming the existing constraint. Changing a constraint is an *edit*, not an add, and a verb that silently overwrote one would be a different verb wearing this name.
  - **the new dependency is unsatisfiable while the existing pins are held** — the settled `ConflictReport` narration preceded by the held-pins line, exactly as `update <pkg>` answers it (Doc C §2.2). **The held-pins line is asserted only when holding is actually the reason** (§8 decision 58, Sprint 16): before emitting it, the verb re-resolves the same manifest against the **unheld** snapshot, and emits the line only if that resolution *succeeds*. When it fails too, holding was never the cause — the constraint is unsatisfiable outright — and the plain `ConflictReport` is answered alone. Without the check the line is a guess that reads as a finding, and it leads with `run parley update to move everything` on the commonest error there is, a typo'd package name, where `parley update` cannot help.

  **Already declared with the identical constraint is a success with a line saying so**, exit `0`, the file and lock byte-identical — the `update <pkg>` already-newest precedent, and idempotence is the property that makes `add` safe to put in a script.
- **`exec <script>`** — `ExecutionScope run:` with the script; `CliResult` carries the child's exit code and no lines of its own (the child already streamed to the terminal).

  **The script is a precondition Parley checks itself, before any process is spawned** (§8 decision 56, Sprint 16). If `<script>` is not an existing *regular readable file* — absent, or a directory — the verb answers **one line naming it, exit `1`**, in the settled `'<path>: ...'` grammar every other missing-file diagnosis uses, and **spawns nothing**. This is not a retreat from §8 decision 45, which stands unchanged: the child's exit code remains a faithful pass-through, and Parley still never claims to know whether a script that *ran* succeeded. It is the boundary before that one. The distinction is what makes it necessary rather than merely tidy: decision 45's documented consumer constraint — a script whose success matters ends with an explicit `ObjectMemory quit:` — is **unavailable precisely here**, because a file that does not exist cannot carry a guard, so without this check there is no discipline an operator could adopt to make `parley exec typo.st` fail. On this toolchain it answers exit `0` and prints `gst: Couldn't open file`, and a directory argument answers exit `0` silently.

#### The inspection verbs (Sprint 11)

Three verbs that **read and explain, never change anything**. All three load the manifest, read `parley.lock` through the §4.1 validated boundary, and take the source's snapshot — they are allowed to consult the index precisely because none of them is `install`, whose fast path is law-bound not to (§8 decision 37). None writes a file, spawns a process, or mutates the store.

- **`why <pkg>`** — the dependent chains that put `<pkg>` in the lock. Renders one line per chain, root first, arrow-joined, each hop naming the constraint that demanded the next: a package pinned only because the root asked for it renders one short chain; a diamond renders two. A package not in the lock is a one-line diagnosis at exit `1` naming it (it is the operator's question about a package they do not have, not a defect). Chains are rendered in sorted order so the output is byte-stable.
- **`tree`** — the pinned graph root-down, one line per node, two-space indent per level, each node `<name> <version>`. A package reached more than once is rendered at each site (the tree is a tree, not a DAG rendering) with repeats marked, so the output cannot mislead about depth. Byte-stable: children sorted by name.
- **`check`** — the verb spelling of the pin fast path, and **the place retirement finally reaches the operator** (§8 decision 37 named it). It reports, in order: whether `parley.lock` exists and validates; whether `PinVerification of: manifest lock: resolution` holds; and **which pinned releases the index now marks retired**, with the author's reason from the settled `retirementReasonFor:version:`. All good ⇒ one confirmation line, exit `0`. Anything wrong ⇒ the problems as lines, exit `1`. A retired pin is a **problem**, not a warning: `check` exists to be run in CI, and an exit code that ignores a retirement would make the verb useless for the one job it has.

**All three on a lockless project** answer the one line `parley.lock is missing - run parley resolve to write it`, exit `1`. The graph comes from the lock, so without a lock there is nothing to inspect, and the repair for *absence* is `resolve` — the verb that writes a first lock — not `update`, which is the repair for a lock that exists and is *corrupt* (§4.1 above, and the `init` shape of §8 decision 31).

**`check` batches; the lock boundary does not (§8 decision 44).** `check` answers *every* problem it finds — the `PinVerification` problems first, then one line per retired pin in pinned-name order — where the lock read answers only its first defect. The two are not inconsistent: the lock boundary reports on one file the operator is about to repair by hand, and the repair is the same whichever defect is named first, while `check` reports on the *state of a project* for CI, where a first-problem-only answer would hide the rest and turn one red build into three.

**Where the graph comes from (§8 decision 40).** `why` and `tree` walk the **lock plus the snapshot**, never the `ConstraintLedger`. The ledger is transient — discarded when the search answers — and `Resolution` carries only the root name and `(version, sha256)` triples. Re-resolving to rebuild provenance would explain a world the operator is not running, since a fresh resolution may legitimately pick a different set than the lock pins. The edges come from the settled `IndexSnapshot>>dependenciesOf:version:`; the root's own edges come from its manifest. No resolver change, no new resolver state.

### 4.2 `CommandLine` — the wiring, as an object (Sprint 8)

The wrapper used to hold the wiring *and* the flag grammar *and* the error boundary, and was declared "glue, excluded from SUnit obligations". That declaration was wrong and it cost: the hardcoded file-in list silently missed `src/publish/`, so the shipped `publish` verb answered a `doesNotUnderstand:` backtrace — **and exited `0`**. Untested glue that decides an exit code is not glue; it is the product. Everything the wrapper did except loading, printing and exiting now lives in an object with laws.

- `CommandLine class >> in: aWorkingDir runner: aProcessRunner` — the working directory (`Package.st`, `parley.lock`, and the `.parley/` state beneath it) and the one process seam, held immutably. Construction is **pathname-passive**: no I/O, no process. Class-side construction; zero public setters; no value equality (the decision-23 precedent).
- `run: anArgvArray` — the whole wrapper's logic as a value-answering message: strip a leading `--`, parse the flag grammar out of the argv, wire the real collaborators, send `CLI run:`, and map anything that escapes to a diagnosis. Answers a **`CliResult`** — it never prints and never terminates the image.
  - **Flag grammar (MVP):** `--source <dir>` ⇒ a `DirectorySource` over `<dir>`; `--git <repo>` ⇒ a `GitIndexSource` over `<repo>` (Sprint 9); absent ⇒ `nil` (the verbs that need none still run). The two are **mutually exclusive** — both given is a usage error, exit `2`, because silently preferring one would make a typo look like a working command. The remaining arguments are the verb argv handed to `CLI run:` unchanged.
  - **The source flags are a declared table, not a chain** (Sprint 9): `CommandLine class >> sourceFlags` maps each flag to the source class it builds, and a **drift law** requires every `*Source` class shipped in `src/source/` to appear in it. Sprint 8's `bin/` drift law covers *directories*, and `GitIndexSource` proved a class can sit inside a named directory and still be unreachable because no flag builds it. Directories and flags are two different reachability questions and each needs its own law.
  - **The two question flags — `--version` and `--help` — are answered ahead of verb dispatch and before any state directory is created** (§8 decision 57; `--version` Sprint 15, `--help` Sprint 16). Asking a tool what it is or how to use it is not running a command in a project: neither needs a working directory, and a `.parley/` created by a question is state created by a question. Both answer **exit `0`** — `--version` one line, `--help` the pinned usage lines. `-h` and the bare verb `help` are accepted spellings of `--help`, because a user who guesses one of the three has asked the same question. **Exit `0` is the whole point of the ruling:** the usage text was already printed for `--help`, but at exit `2`, so the first command a new user types failed any `set -e` script or CI smoke check while `--version` beside it succeeded — the tool disagreeing with itself about whether a question is an error. **What stays exit `2` is unchanged and is the other half of the line:** `parley` with no argv at all, an unknown verb, and a *trailing* `--help`/`--version` on a verb (`resolve --help`) are all still usage errors, because failing to say what you want is an error even though asking for help is not. These are declared special cases recognized once, never a general "valueless flags are grammar now" change — the settled `valueOf:in:` trailing-flag behaviour is held unchanged by law.
  - **Wiring:** store at `<aWorkingDir>/.parley/store`, target at `<aWorkingDir>/.parley/packages` (created when absent), the git cache at `<aWorkingDir>/.parley/git/<sha256 of the repo location>` (Sprint 9 — the settled `Sha256` keys it, so any repo string becomes one deterministic filesystem-safe name and no escaping layer is invented), the injected runner. Deriving both from the working directory rather than the process's cwd is what makes the wiring law-testable under `tmp/`.

#### The diagnosis boundary

**No Parley command ever answers a backtrace, and no failing command ever exits `0`.** `run:` maps every outcome onto exactly three shapes:

| Outcome | `lines` | `exitCode` |
| --- | --- | --- |
| Success | the verb's own lines | `0` |
| Usage (unknown verb, wrong arity, source-requiring verb with no source) | the pinned usage lines | `2` |
| A **diagnosed** problem — the verb answered it, or a declared Parley error reached the boundary | the problems / the message | `1` |
| An **undiagnosed** error — anything else reaching the boundary | one line naming the error's class and message text (wording pinned in RED) | `70` |

- The **declared Parley errors** are `ManifestError`, `SourceError`, `InstallError`, `ExecutionError`, `PublishError` and — from Sprint 9 — `LockError`. An error carrying `problems` contributes those as the lines; one carrying only a `messageText` contributes that as a single line. Exit `1` — the tool understood what went wrong and is telling the operator.
- Anything else is a **defect in Parley**, not in the operator's project: exit **`70`** (`EX_SOFTWARE`), distinct from `1` so a script can tell "your input is wrong" from "the tool is broken". Still one line, never a backtrace: Parley diagnoses, it does not dump.
- The boundary is a **closed set with a law**: every `Error` subclass defined in the `Parley` namespace is either mapped to exit `1` here, or is **declared undiagnosed with its ground named** — either *provably never signaled out of a verb*, or *reaching exit `70` by a named escape path that is accepted, for now, as fail-stop*. The two lists must partition the enumeration, so a new error class can never drift into the `70` bucket silently: the law fails first, and whoever adds the class must decide which list it belongs to and say why.

  **Sprint 9 restores the strong claim.** The two boundaries above — the lock read (§4.1) and the authoring file-in (§3) — remove all three named escapes, so from Sprint 9 every undiagnosed class is *provably never signaled out of a verb* and the weaker second ground has no members. It stays written down because the law must keep accepting it: the next error class to arrive may legitimately need it, and a partition rule that silently has only one branch is a rule nobody remembers is there.

  **What the closed set does not cover, and the law that covers it (§8 decision 35).** The claim, and the law that enforces it, quantify over `Error` subclasses **defined in the `Parley` namespace**. A *kernel* error raised inside a verb is outside the enumeration entirely, so it reaches exit `70` without any law noticing — which is exactly how the malformed-body `parley.lock` of §4.1 survived Sprint 9. "Every Parley error class is diagnosed or provably never signaled" is a strictly weaker statement than "every operator input is diagnosed", and the two must never be conflated. Enumerating more error classes does not close the distance: it could not have caught that bug and will not catch the next one.

#### The deserialization-boundary law (Sprint 10)

The invariant that carries the weight is **per boundary, not per class**: *every point where Parley reads a file the operator can edit validates shape before handing the value to a constructor, and answers a diagnosis at exit `1` on malformed content.*

Like Sprint 8's `bin/` directory law and Sprint 9's `sourceFlags` law, it needs its own enumeration rather than a widened neighbour. The anchor is mechanical: **`IndexEntryReader readFrom:` is the single literals-only parser**, so every sender of it in `src/` is a deserialization boundary by construction. `CommandLine class >> deserializationBoundaries` declares them, and the law reads `src/` and requires every sender to appear in the table — a new reader of an operator-editable file can never again ship without a diagnosis. The two senders today are the `CLI`'s `parley.lock` read (§4.1) and the `DirectorySource` scan (Doc F §4/§4.1); `ManifestFile load:`'s `Package.st` (§3) is the third boundary and is declared alongside them, because it reads an operator-editable file by a different mechanism (file-in, not the reader) and is exactly the kind of boundary a reader-anchored enumeration would otherwise miss.

The search runs over `codeOf:` the file — comments and string literals stripped — because Doc E anchors on *senders* and prose naming a send is not one (§8 decision 38), and over **whitespace-normalized** text from Sprint 11, so a receiver and selector split across lines are still one send (§8 decision 43). There is no reflective alternative on 3.2.5: `whichSelectorsReferTo:` searches literals rather than sends and finds none of the real senders, and `allCallsOn:` does not exist. The law's claim is therefore bounded and stated as bounded — *every textually spelled sender is declared* — with the indirect send answered by a convention (every sender spells its receiver) that the enumeration's pinned answer polices.

Each declared boundary owes one law: a malformed input reaches its verb and is answered at exit `1`, blaming nobody but the file. Together they are what lets Parley claim the sentence users actually rely on — *no operator file ever produces a backtrace, an exit `70`, or a lie about whose fault it is*.

  The weaker second ground was chosen at the Sprint 8 RED review over a claim the code could not support. Of the five currently undiagnosed classes, `ConstraintFormatError` and `VersionFormatError` meet the strong claim — every caller inside a verb catches them. Three do not, and their escape paths are declared rather than hidden: `IndexEntryParseError` and `IndexEntryFormatError` escape the `CLI`'s `parley.lock` read, and `ManifestVocabularyError` was declared to escape `ManifestFile load:` when the author's own `Package.st` has a typo. **The third declaration was factually wrong, and the Sprint 9 RED review corrected it** (§3): `ManifestVocabularyError` never escapes `load:` at all — the file-in swallows it, gst prints a backtrace, and `load:` answers a *different*, untrue diagnosis at exit `1`. The disease was worse than declared, not milder: not exit `70` blaming Parley, but a confident wrong sentence about the author's file, preceded by the backtrace this boundary exists to abolish. The two lock escapes are exactly as declared and do land on exit `70` — nonzero, one line, no backtrace — so for those the fail-stop invariant held and no script was lied to about success. What they lack is the *right blame*: they are the operator's problems reported as Parley's. Reclassifying them as exit-`1` diagnoses needs a lock-validation boundary and an authoring-error boundary, which is design and not a fix; it is a **ruled gap carried out of Sprint 8**, not a licence to leave the list vague.
- The mapping is expressed as **`on:do:` handlers**, never an `isKindOf:` chain. Smalltalk's exception system already *is* the taxonomy; re-implementing it as branching would be the kind-branching the architecture bans, and would silently mis-handle a subclass. `CommandLine` classifies by handling, and the one thing it decides is which of the four shapes above the outcome takes.

`CommandLine` is a **composition root**, not a manager: it holds no domain state, makes no domain decision, and answers a value. It exists because the wiring and the boundary are decisions — and decisions belong in objects with laws, not in a script nobody tests.

### 4.3 The executable wrapper (genuinely thin)

`bin/parley` (POSIX sh, ~3 lines) execs `gst -f bin/parley-main.st -- <argv>`; `parley-main.st` lives in `bin/` — NOT `src/exec/`, whose every `.st` the test harness files in, and a main script executes on file-in. It does exactly four things and holds no logic:

1. file in **every** directory under `src/`, in load order;
2. send `CommandLine in: <cwd> runner: ProcessRunner new` `run: <argv>`;
3. print the result's lines;
4. `ObjectMemory quit:` the result's exit code.

Printing and exiting happen **here alone**. The file-in list stays explicit because load order is semantic, and it is **law-guarded**: a law reads the wrapper's own source and requires every existing `src/` subdirectory to appear in it, so a new `src/` directory can never again ship unreachable. (Per-invocation file-in is the honest MVP cost; a prebuilt image is deferred tooling polish.)

## 5. SUnit Requirements for This Doc

- **`ProcessRunner`:** real execution laws — a command exiting `7` answers `7`; success answers `0`.
- **`ExecutionScope`:** the pinned child command composition (pure, exact string); `register` executes the real plan (real `gst-package`, real archive bytes land byte-identical in the target as `<name>.star`); fail-stop on the first failing command (real: staging copies garbage bytes fine, then `gst-package` exits `1` on the non-archive — the `ExecutionError` names that registration command and code; later commands never run); `run:` really launches the curated child (a script leaves a sentinel; the exit code comes back).
- **`ManifestFile`:** loading a written `Package.st` answers the built manifest (round-trips name/version/dependencies); a define-less file signals the pinned error; **an absent path signals the pinned one-problem `ManifestError` before any file-in is attempted** (Sprint 8) — observable at the boundary as exit `1`, never `70`; **a `Package.st` sending an out-of-vocabulary selector signals one `ManifestError` carrying the vocabulary error's message and suggestion** (Sprint 9), and the same input through the shipped binary exits `1` with no backtrace; **a `Package.st` whose declarations fail validation (e.g. `version: 'banana'`) signals the builder's own `ManifestError` with every problem in the batch preserved** (Sprint 9) — never the define-less diagnosis, and never a backtrace.
- **The lock boundary (Sprint 9):** an unparseable `parley.lock` and a wrong-tag `parley.lock` each signal one `LockError` naming the path and the reader's message, on `install` and on any verb that reads the lock; `update` is unaffected by a corrupt lock and repairs it (it never reads one); the diagnosis names `parley update`. Observable at the §4.2 boundary as exit `1`, never `70`.
- **Lock body-shape validation (Sprint 10):** each §4.1 shape violation — a missing key, keys out of the §5.4 order, a non-Array `#packages`, a package tuple of the wrong arity, a missing `#sha256` marker, a non-String field — signals one `LockError` naming the path and the defect, at exit `1`; an unparseable `#version` inside a shape-perfect lock does the same (the Doc F §4.1 lesson); a lock Parley itself wrote always passes, proved against the settled writer's own output rather than a hand-copied literal. `Resolution fromLockEntry:` is never reached with an unvalidated value.
- **The inspection verbs (Sprint 11):** `why` renders the pinned chains for a diamond as two sorted, byte-stable lines and one line for a root-only dependency; `why` on a package absent from the lock is exit `1` naming it; `tree` renders the pinned graph root-down with two-space indents, children sorted, repeats marked; `check` answers exit `0` and one line on a healthy project, exit `1` with the problems on a missing/invalid lock, on a failing `PinVerification`, and **on a pinned release the index marks retired** — carrying the author's reason verbatim; all three are proved to change nothing (a recording runner spawns nothing, and the working directory is byte-identical afterwards); and **`why`/`tree` never consult the `ConstraintLedger`** — provable because the resolver is never entered (a resolver double that signals if called).
- **`SchemaShape` (Sprint 11):** `isString:`, `isStringArray:` and `isHexDigest:` as pure predicates with their own laws (64 lowercase hex accepted; wrong length, uppercase, and non-hex characters each rejected); and the **single-definition law** — neither `CLI` nor `DirectorySource` re-implements them, provable by both validators answering identically for the same value.
- **Hex digest validation (Sprint 11, §8 decision 42):** a lock whose `#sha256` is not 64 lowercase hex characters is one `LockError` naming the path and the defect, at exit `1`, **before** `verifyHash:` is ever reached; an entry whose `#archive` digest is malformed is one batched `SourceError` problem; and the settled corruption wording is unchanged for the case that really is corruption (a well-formed digest that does not match its bytes).
- **Selective `update <pkg>` (Sprint 12, §8 decision 46):** the named package moves to the newest version its constraints allow while **every other pin stays byte-identical** (asserted against the pre-update lock, tuple by tuple, not merely "the lock changed"); a transitive dependency the root never declared can be named; a package absent from the lock is exit `1` naming it; a lockless project answers the pinned missing-lock line; already-newest is exit `0` with its own pinned line and a byte-identical lock; holding the rest unsatisfiable answers the settled `ConflictReport` narration **preceded by** the pinned held-pins line; the whole verb installs and registers exactly as `update` does. Plus the two purity laws: the narrowed snapshot is a **new** value (the receiver still answers every version afterwards), and **a held pin that is retired is still offered** — narrowing outranks the §2.1 retirement filter, so an unrelated retirement can never fail a selective update.
- **The deserialization-boundary law (Sprint 10):** every sender of `IndexEntryReader readFrom:` in `src/` appears in `CommandLine class >> deserializationBoundaries` (the drift law — it must fail against a table with a row removed), and every declared boundary has a law driving a malformed file through a real verb to exit `1` with no backtrace and no blame on Parley.
- **`CommandLine` source flags (Sprint 9):** `--git <repo>` wires a `GitIndexSource` whose cache is `<workingDir>/.parley/git/<sha256 of repo>` (nothing beside the process cwd); `--source` and `--git` together answer usage, exit `2`; and the **source drift law** — every `*Source` class shipped in `src/source/` appears in `CommandLine class >> sourceFlags`, so a source can never again be lawful and unreachable.
- **`CLI`:** every verb law — init template + refusal; resolve's byte-stable lock oracle and conflict narration; the fast-path skip proof (valid lock + primed store + a source double failing both `snapshot` and `fetch:version:` ⇒ success); stale-lock re-resolution; the corruption fail-stop; update re-pinning what install would keep; exec propagating the child code; usage/exit-2 shapes.
- **`CommandLine` (Sprint 8):** the wiring laws — `publish` reaches a real `Publisher` through the wiring (the shipped defect, closed); `--source <dir>` still wires the settled verbs; the store and target land under the *working directory*, not the process cwd. The boundary laws — a declared Parley error becomes its problems and exit `1`; an undeclared error becomes one pinned line and exit **`70`** (provable with a runner double signaling a plain `Error`); **no failing outcome ever answers exit `0`**. The closed-set law: every `Error` subclass in the `Parley` namespace is accounted for by the boundary.
- **The shipped binary (Sprint 8):** laws that run `bin/parley-main.st` itself as a child process through `ProcessRunner` — success exits `0`, a diagnosed failure exits nonzero, and neither prints a backtrace. Plus the drift law: the wrapper's own source names **every** existing `src/` subdirectory. These are the only laws that test glue, and they exist because glue that chooses an exit code is not glue.
- **End-to-end (the sprint's exit):** entries + a real archive (a toolchain-**built** `.star`: `gst-package --target-directory <dir> <pkgdir>/package.xml` builds `<dir>/<name>.star` from an authored package.xml + `.st` file — lowercase internal name per Doc B §3.4 and the name-equality constraint, Doc D §4) → resolve → lockfile → install → register → a curated child proves the package's class is visible — **a package lands in an image**. System stars are never copied as fixtures: their capitalized internal names violate §3.4 under name equality.
- **Digest discipline (amended for real archives):** authored opaque byte strings keep operator-verifiable pinned digest literals (Doc D style); toolchain-built `.star` bytes vary by machine, so their entry digests are computed at fixture time through the **settled, vector-anchored** `Sha256` — never pinned as literals, and never used to test `Sha256` itself.
- **Hygiene:** every directory (working dirs, stores, targets, child images) lives under `tmp/`, unique per test, removed in tearDown; `tmp/` empty or absent after a clean run. **The developer image is never mutated**: no test files a package into the harness image; real processes appear only where the law under test IS execution, and always confined to `tmp/`.
