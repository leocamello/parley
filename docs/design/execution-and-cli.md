# Parley Design — Execution Scope & CLI

> **Scope:** `ProcessRunner`, `ExecutionScope`, `ExecutionError`, `ManifestFile`, `CLI`, `CliResult` — the Phase 3 closer (Sprint 6) — plus `CommandLine` and the diagnosis boundary (Sprint 8) and `LockError` (Sprint 9). All classes in the `Parley` namespace, all in `src/exec/`; structural immutability applies throughout (class-side construction; zero public setters). This document is where Parley finally touches the operating system: it defines the ONE process seam, the curated child `gst` invocation, the resolution of the deferred `gst Package.st` caveat (§8 decision 19), and the command-line verbs wired over Sprints 0–5. Every 3.2.5 mechanic pinned here was verified empirically against the toolchain at staging (issue #8).

---

## 1. `ProcessRunner` (the one process seam)

The **only** pathway in all of Parley by which a child process is ever created. Everything above it composes command lines as pure string values; everything at it is one thin, dumb executor.

- `ProcessRunner class >> new` — stateless; exists as an instance so tests can substitute a recording/failing double.
- `run: aCommandString` — executes the command via the 3.2.5 kernel's `Smalltalk system:` and answers the child's **exit code** as an Integer. 3.2.5's `system:` answers the raw wait status (exit code × 256); `run:` normalizes it: `status // 256`. `0` is success; nothing is signaled — the code is an answer, and its meaning belongs to the caller.
- No output capture in MVP: the child's stdout/stderr flow to Parley's own (the CLI is a terminal program). No shell-quoting layer: Parley composes its own command lines from paths it controls.
- **Plumbing chatter is discarded on the composed line, never captured** (Sprint 19, §8 decision 63): a command line composed for a child that is *not* the user's program — `Publisher`'s five build lines, the registration plan's `install -c` echo — carries a **stdout redirect appended by its composer at the point of execution**. Nothing is buffered, stderr is never redirected (a failing child's diagnostics always reach the terminal), no user text is interpolated, and the seam itself is untouched: `run:` still executes what it is given and answers the exit code. This narrows the sentence above rather than contradicting it — *capture* stays deferred; *discarding* is ruled in. `exec`'s child needs neither: its GC chatter is suppressed at the source by a composed flag (§2.2, §8 decision 77). **The tail has two definitions and that is ruled rather than tolerated** (§8 decision 78): each composer owns it, the seam must not, both are pinned against one test oracle so neither can drift, and a **third** composer appending the same tail is the trigger to extract. **The rule's domain is every class in `src/` composing a line run through the seam, and it is five, not three** — `Publisher`, the registration plan, `ExecutionScope>>childCommandFor:`, `SparseIndexSource` (already silent: `curl -sfS` drops progress and keeps errors) and **`GitIndexSource`, which Sprint 19 did not reach**: `git clone` and `git -C … fetch` still write `Cloning into '<cache path>'` and `done.` to stderr, naming a `.parley/git/<sha256>` path the operator never chose. Carried gap, ranked and unscheduled at Sprint 19's close-out; the fix is `--quiet` on both composed lines, probed to answer zero bytes on both streams while a failing clone still writes `fatal: …` to stderr at exit `128`.

## 2. `ExecutionScope` (the curated child image)

The honest `bundle exec` for 3.2.5 (§8 decision 16), and the single home of invocation logic. A scope holds three collaborators immutably:

- `ExecutionScope class >> on: anInstalledSet target: aTargetDir runner: aProcessRunner`.

### 2.1 Registration (executing Sprint 5's plan)

- `registrationCommands` — exactly `anInstalledSet registrationCommandsFor: aTargetDir` (the Doc D §4 plan; a pure value).
- `register` — runs each plan line, in the plan's order (sorted package-name order, each package's staging line immediately before its registration line — Doc D §4), through the runner. The first nonzero exit signals one **`ExecutionError`** naming the exact command line and the exit code; later commands are not attempted. **Fail-stop, not batched:** an execution failure is environmental (a broken toolchain, an unwritable disk, a corrupt archive rejected by `gst-package`), unlike install problems, which are per-package data problems — retrying the rest teaches nothing and can half-register an environment. Empirical anchor (issue #8 ruling): 3.2.5's `gst-package` validates the archive (a `.star` is a zip) and exits `1` on a non-archive file (`gst-package: Invalid argument`) — the staging line copies any bytes, so garbage fails precisely on the registration line. Note the flagless mode: 3.2.5's option parser accepts **no** `--install` spelling; install is the default mode, and the `--help` text claiming the flag is stale upstream.
- Registration is (re-)runnable: the staging copy and `gst-package --target-directory` both overwrite identical files harmlessly (verified). Switching or rolling back an environment re-points at a different target — it never mutates one. The `.parley-staging/` directory the plan writes under the target is invisible to the child (`PackageLoader` scans the image directory for `*.star` files only) and is left in place — target-confined residue, not state.

**The registration lines are plumbing, and `register` silences their chatter at execution** (Sprint 19, §8 decision 63). `gst-package` echoes its own `/usr/bin/install -c …` copy line to stdout — text on the operator's terminal that Parley did not write, probed pre-RED as originating here and **not** in `Installer`, which composes no command line at all. `register` appends the stdout redirect to each plan line **as it runs it**: the plan (`registrationCommands`) stays the pure value Doc D §4 pins, and a failing line's `ExecutionError` names the **plan line unchanged**, so the settled diagnosis and the settled plan laws are byte-identical. `gst-package`'s failure diagnostics are on stderr and untouched.

### 2.2 The child invocation

- `childCommandFor: aScriptPath` — the pinned composition, exact:

  ```
  gst -g -i -I <aTargetDir>/parley.im --no-user-files <aScriptPath>
  ```

  Why each element (verified against 3.2.5; corrected by the issue #8 ruling; `-g` added by §8 decision 77, Sprint 19): **`-g` (`--no-gc-message`) suppresses the image rebuild's `"Global garbage collection... done"` chatter at the source** — probed on this exact shape: stderr drops to zero bytes, stdout and the exit code are unchanged, and the script's own streams pass through untouched, which is why `exec` needs no redirect and crosses nothing the *output capture* deferral governs. `-I <target>/parley.im` places the image in the target directory, and 3.2.5's `PackageLoader` local package registry follows the image directory — every `.star` sitting there is visible to the child **by its filename**: `Kernel.StarPackage` requires the `package.xml` name to equal the filename basename (`kernel/PkgLoader.st`), so a package is loadable iff `<target>/<InternalName>.star` exists. This is why Doc D §4's plan registers each archive under its true name — a content-addressed `<sha256>.star` is invisible to the child. `--no-user-files` excludes `~/.st` customizations. `-i` rebuilds the image from the kernel every run: no state leaks between runs, and the scope needs no image lifecycle management. The platform's system packages remain visible to the child — they are the host runtime, as a language's standard library is under any `bundle exec`.

- `run: aScriptPath` — `runner run: (childCommandFor: aScriptPath)`, answering the child's exit code. A nonzero child is the script's own business — an answer, never an `ExecutionError`.

## 3. `ManifestFile` (decision 19 resolved)

`ManifestFile class >> load: aPath` reads the developer's **own** `Package.st` and answers its `LibraryManifest`:

0. **check the path first** (Sprint 8): if `aPath` does not exist or is not readable, signal a one-problem `ManifestError` naming the path and the verb that writes one (exact wording pinned in RED). **The readability half of this sentence went unimplemented from Sprint 8 to Sprint 16** — the code checked `exists` alone while the pinned diagnosis promised `missing or unreadable Package.st`, so the tool asserted a check it had not made. Probed at the Sprint 16 GREEN review: a `Package.st` the reader lacks permission to open answers `internal error: FileError: could not open <path> - this is a defect in Parley, not in your project` at exit `70`, and a directory-shaped one answers the same with `PrimitiveFailed`. Both are ordinary operator states (a bad umask, a root-owned checkout, a stray `mkdir`), and both were answered by Parley blaming itself. The predicate is now the same one §8 decision 56 gives every file boundary — a regular readable file — and **the pinned wording does not change**, because it was already telling the truth about what this step was supposed to do. This is the sprint's **third declared settled-class exception**, granted at the Sprint 8 RED review. It exists because 3.2.5's `FileStream fileIn:` signals `SystemExceptions.FileError` — a *kernel* error — on a missing file, so without this check the most ordinary user error in the tool (`resolve` before `parley init`) reaches §4.2's boundary as an **undiagnosed** error and is answered with exit `70`: *"this is a defect in Parley, not in your project."* That is the fail-wrong disease in its second form — not a lying exit code, but a lying attribution of blame. A missing `Package.st` is the operator's problem and Parley must say so: exit `1`, one problem, naming the fix.
1. clear the recorded manifest;
2. file the path in with `Namespace current: Parley` — inside the namespace the token `Parley` resolves to the `Parley.Parley` gateway (§8 decision 19), so the Doc B §2 syntax works verbatim — **and with the toolchain's `Transcript` rebound for the duration of that block** (Sprint 18; §8 decision 61, and §3.1 below);
3. answer the authoring error the file-in captured, if any (below); **then, if the capture yielded a file-and-line anchor, the re-voiced anchor diagnosis — a recovered anchor means the load failed, whatever the file managed to record** (Sprint 19, §8 decision 76); then the manifest recorded by `define:`; if the file recorded nothing (no `define:` reached), signal a one-problem `ManifestError`-style error naming the path (exact wording pinned in RED).

**The authoring-error boundary** (Sprint 9, closing half of the decision-32 gap): an author error inside the developer's own `Package.st` — a selector outside the manifest vocabulary (`ManifestVocabularyError`), or a declaration that fails validation (`ManifestError` from `ManifestBuilder>>build`) — is answered as the author's diagnosis at exit `1`, carrying the original error's own text unchanged. The errors already *read* as diagnoses (`Package.st sent #nmae - not part of the manifest vocabulary. Did you mean #name?`); what was wrong was who they blamed. Nothing about the message changes — only its classification.

**Where the boundary can live (verified against 3.2.5, Sprint 9 RED review).** It is *not* an `on:do:` around the file-in, and the earlier text of this section saying "the file-in of step 2 is wrapped" was factually wrong. The doit context of a filed-in statement is **parentless** — `thisContext parentContext` from inside a filed-in file answers `UndefinedObject>>__terminate`, not the caller of `fileIn:` — so a handler around `FileStream fileIn:` is not in the signaling chain and never fires. gst prints its own backtrace, abandons the statement, and `load:` then answers the *wrong* diagnosis ("no manifest defined" about a file that did send `define:`). `Behavior>>evaluate:` was probed as an alternative and fails identically. Only a handler in a method frame **called by** the filed-in statement catches the error, with the message intact and the file-in continuing.

The boundary therefore lives in `Parley.Parley class >> define:` — the one Parley frame a filed-in `Package.st` enters. This is the sprint's **third declared settled-class exception**, granted at the Sprint 9 RED review: `define:` wraps the builder construction, the author block's evaluation and `build` in one `on: ManifestVocabularyError, ManifestError do:` handler, which hands the error to `ManifestFile` (where all recording state already lives) and returns `nil`. `ManifestFile load:` then signals from **its own** frame, where the handler is real:

- a captured `ManifestVocabularyError` ⇒ one `ManifestError` problem carrying the vocabulary error's message text verbatim, suggestion included;
- a captured `ManifestError` ⇒ re-signaled with its `problems` **intact**, never flattened to one line — the batch report is the whole point of `ManifestError` (Doc B §3.3: an author fixes a `Package.st` per edit-run cycle, not per error).

Two ordering rules make this sound, and both are load-bearing: `load:` clears the captured-error slot alongside `recorded` at entry, so no stale error leaks from a previous load; and it checks the captured error **before** the `recorded isNil` check, or the lying "no manifest defined" diagnosis survives. Where a file sends `define:` more than once, the **first** authoring error wins and is reported even if a later `define:` succeeds — a `Package.st` with a broken `define:` must never half-succeed.

**A third ordering rule joins them in Sprint 19, because the two above have a blind spot the sentence they serve does not** (§8 decision 76). The rules govern the *captured-error slot*, which only an error passing through `define:`'s handler reaches. A `doesNotUnderstand` raised by a top-level statement — a `Package.st` sending `define:` twice where either send raises — never enters that slot: `gst`'s `executeStatements` abandons the statement and continues, `recorded` keeps the value from the send that worked, and the verb exited `0` on the strength of it, discarding the anchor the capture had recovered. So **the recovered anchor is itself checked before `recorded`**: an anchor mined from the capture means the author's program raised, and the load is refused with the re-voiced file-and-line diagnosis whatever else the file managed to declare. The half-succeed sentence above finally has code that can make it false.

**The capture is scoped to a load in progress, and that scoping is part of the design — not an implementation detail.** `define:` is not only the file-in path: it is also the settled live API, and a `Parley define:` evaluated in an image or a test must signal to *its own caller*, which is exactly what the Sprint 1 laws encode. Capturing unconditionally would swallow those signals and silently break that contract. So the boundary asks `ManifestFile isLoading` and captures only when the answer is yes — the one context whose signaling chain is cut; everywhere else it sends `pass` and the error travels untouched. The flag is set around the file-in and cleared in the **`ensure:`**, so a load that fails part-way can never leave the image in a state where live authoring errors vanish. (Found in Sprint 9 GREEN: the ruling as first written said only "`define:` wraps … and hands the error to `ManifestFile`", and taken literally it broke five settled Sprint 1 laws. Written down here so nobody implements the hole again.)

Both classes are therefore never signaled out of a verb, and the §4.2 closed set can say so without qualification.

Sprint 6's exception stands unchanged alongside it: `define:` sends `ManifestFile record: manifest` before answering. All recording state (the holder, the clear, the read, and now the captured authoring error) lives in `ManifestFile`; no domain decision moves into the gateway.

### 3.1 The authoring boundary is where the toolchain speaks, and Sprint 18 gives it Parley's voice

The two rulings and the mechanism are **Doc B §2.2** — read it first; this section states what `ManifestFile load:` owes as a consequence, and it is the spec of record for the *diagnosis shapes*. (Sprint 18's staging plan cited Doc E §4.1 for this; §4.1 is the **verb** list and the write-boundary table, and the authoring boundary has always lived here in §3. The citation was corrected at Gate C rather than left for the coding agent to hit at RED.)

**The capture wraps step 2, and the capture site performs no I/O** (§8 decision 61). `load:` sends `Parley.ManifestCapture` a block containing the namespace swap and the `FileStream fileIn:`, and receives the collected text back as a value. **The `fileIn:` does not move into `ManifestCapture`** — that is the ruling, and the alternative was rejected for two independent reasons. It would make `ManifestCapture` a **ninth** class performing direct `File`/`FileStream`/`Directory` I/O, which fails §8 decision 60's prohibition law outright (the law's search patterns include `'FileStream '` with a deliberate trailing space, so every class-side send counts); and it would put **the author's whole program** inside a class whose declared job is capture, which is §8 decision 73's *precheck yes, translate no* split re-created one level up. `ManifestFile` keeps the send and keeps its census seat; **the census stays at eight.**

**Restoration is unconditional — and *unconditional* is not *immediate*** (§8 decision 75, ruled at a mid-GREEN halt). An `ensure:` runs on the **unwind**, while a handler runs on top of the still-live signalling context, so for an error raised *inside* the capture window the measured order is block, handler, `ensure:` — the swap is still live while that handler runs, and the binding is back by the time it returns. The authoring boundary is unaffected, and that is why it is worth stating rather than glossing: `ManifestFile` signals its diagnoses from its **own** frame after the window has closed, and printing happens in `bin/parley-main.st` after a full unwind, so every handler that composes a diagnosis already sees the real `Transcript`. **The constraint this leaves on future code is stated rather than left to be discovered: a handler for an error raised inside the capture window must not print.** Restoring earlier would mean catching the error inside `ManifestCapture`, which wraps the author's whole program in a broad catch — refused by decision 61, and refused for *that* reason rather than for swallowing, since `pass` swallows nothing.

**Restoration is unconditional, and that is the one failure mode worth a scenario of its own.** `ManifestCapture` restores the previous binding in an `ensure:`, so an error raised *past* the gateway's own handlers — an error outside any `define:` block, a `ManifestError` re-signaled from `load:`'s own frame — still leaves `Transcript` bound to the real one. **A leaked swap does not fail loudly: it silences the rest of the process**, which in this suite means a whole run of laws asserting on output they can no longer see. It is checked on the failure path and on the non-local-exit path separately.

**Every authoring diagnosis names the path, and it does so by being batched rather than re-toned** (§8 decision 44's settled shape, already used by the source scan). `ManifestBuilder`'s problems — `missing required field name`, `missing required field version`, `invalid version 'nope'`, `invalid constraint 'garbage' for dependency 'demo'` — are the only diagnosis family in the tool that never names the file the author must open. They are now emitted inside the settled per-file batch: a header naming the path and the problem count, then one line per problem, **each problem sentence byte-identical to its settled literal**. The path is *added around* them; none of the four is rewritten, because an author fixes a `Package.st` per edit-run cycle and the sentences already say the right thing about each field. A **single**-problem manifest answers the batch shape too — decision 44 gives a file one shape, not two, and a bare line for `N=1` is how a shape acquires a second form nobody declared.

**The structural claim, and what it is measured on.** No diagnosis the authoring path can produce may reach the operator without naming a path, and **no backtrace frame or Parley source path may reach the terminal at all**. The second half is asserted over **captured stdout *and* stderr from the shipped binary**, never over the `CliResult`'s composed `result lines` — asserting over `result lines` is precisely the defect that let eleven lines of kernel text ship past laws that deny backtraces (Doc B §2.2). The two fragments that remain — `primError`'s `Object: <receiver>` prefix on stdout, and the C-level parser's `<path>:<line>: parse error` on stderr — are named in Doc B §2.2, in the README, and **in the law's own comment**, so the law's bound is stated rather than discovered (§8 decision 43's standard). **The first is terminated before Parley composes** (Doc B §2.2, amended at the Sprint 18 RED review): it arrives without a trailing newline, so `load:` ends the dangling line whenever it recovers a file-and-line anchor from the capture, and the kept fragment occupies a line of its own instead of fusing with the diagnosis. That is what lets S1 assert the captured stdout **exactly** rather than by substring containment.

**Trust boundary unchanged** (architecture §2.2): only the root application's own manifest is ever loaded this way — the file its author owns and runs. Third-party `Package.st` files are never evaluated by anything (their information enters only as static index entries through the literals-only reader); the hard bans still hold — file-in of the owner's manifest is the authoring path Doc B §2 always specified, and no third-party byte ever reaches it.

## 4. `CLI` and `CliResult`

- `CLI class >> in: aWorkingDir source: aPackageSource store: aContentStore target: aTargetDir runner: aProcessRunner` — every collaborator injected (`source` may be `nil` for verbs that need none); tests pass doubles, the executable wrapper passes the real ones. The CLI reads `Package.st` and `parley.lock` in `aWorkingDir`.
- `run: anArgvArray` — dispatches the verb and answers a **`CliResult`**: an immutable value carrying `lines` (Array of Strings — everything the wrapper should print) and `exitCode` (Integer). The CLI **never** prints, never terminates the image, and never touches a process except through the scope's runner: it is an orchestration answering a value. Argv grammar: `init` | `resolve` | `install` | `update [<pkg>]` | `add <pkg> <constraint>` | `remove <pkg>` | `search <term>` | `info <pkg>` | `outdated` | `exec <script>` | `publish <dir>` | `why <pkg>` | `tree` | `check`. An unknown verb, a missing `exec` script, **wrong arity** (`update` takes at most one package), or a source-requiring verb with no source answers the pinned usage lines with exit code `2` — and the `verbs:` line renders the optional argument exactly as this grammar spells it, `update [<pkg>]`. **From Sprint 21, `resolve` is no longer source-requiring** (§8 decision 83): its `verbRows` guard matches with or without a source, so the `#needsIndex` ground stops firing for it by decision 81's own derivation, and the index requirement becomes a declared refusal *inside* the verb at exit `1` (§4.1). **From Sprint 21, `check`, `tree` and `why` are not source-requiring either** (§8 decision 84, ruled mid-sprint when decision 83's trigger fired inside the sprint that set it): a path-only project resolves flagless and must be inspectable without inventing an empty index, so their `verbRows` guards drop the source predicate and the index requirement becomes the same declared refusal inside the verb at exit `1` (§4.1). **The write verbs — `install`, `update`, `add`, `remove` — are unchanged**, and `install` is the mirror's remaining member with its trigger restated; the bound is held by law, S33's source-less `install` still answering the `#needsIndex` usage error. **`search`, `info` and `outdated` are unchanged for a different reason**: they are index questions by Doc C's matrix — a project with no index has nothing for them to answer — and `outdated`'s published column *is* the index's answer.

**A usage error names what was wrong on line one, above the block** (§8 decisions 79 and 81, Sprint 20). The block above is good reference and a poor diagnosis: probed through the shipped binary at Sprint 20's Gate C, **no verb at all**, **an unknown verb**, **a known verb given arguments it does not take** and **a source-requiring verb with no source** answered *byte-identical* output, so the tool told the operator what it offers and never what they did. Each of the **four** now carries its own first line, distinguished rather than merged, because *"you typed a verb that does not exist"* and *"that verb needs an index and you gave none"* have different repairs. The fourth ground is the one decision 79 first omitted and decision 81 restored: `parley exec`, `parley publish` and `parley resolve --help` each name a verb the tool really has, and `resolve --help` answers usage **even with a source wired**, so its ground is the arity and not the index. **Two more usage answers are decided outside this grammar and carry their own declared reasons** — both source flags given, refused in `CommandLine>>dispatch:` before any verb exists, and an unrecognized `--layout` value, refused inside `publish:layoutNamed:` after a verb row matched. All six reasons are **one declared table consumed twice** (§8 decision 81); none is composed at the site that refuses. **The block itself is unchanged apart from its verbs row**, and the relationship is stated so a law can rest on it: a usage error is **one reason line followed by the block**, and `--help` is **the block alone** (§4.2). Laws locate the block by its start, or assert that an answer ends with it — **never by absolute line index**, which is a claim about a neighbour rather than about the thing being asserted. **The usage lines name the source flags**, not only the verbs: `--source`/`--git` are how the most common verbs reach an index, and a usage message that lists `resolve` while hiding what `resolve` needs leaves the operator exactly as stuck as no message at all.

### 4.1 Verbs

- **`init`** — writes a **starter skeleton** `Package.st` in the working directory; refuses (one line, exit `1`) if the file exists. The skeleton is deliberately **not** Doc B §2's illustration. That example declares `kernel-json` with two dependencies that exist nowhere, so `init` followed immediately by `resolve` failed on phantom packages — the worst possible first run, and unnoticed because the round-trip law asserted the *illustration's values* rather than the *template's fitness*. A template's job is to be a correct starting point, not a feature tour; the dependency syntax is taught in the skeleton's header comment, where it costs nothing to read and nothing to resolve. Two laws now split the claim: Doc B §2's syntax still round-trips through `load:`, **and** what `init` writes loads and declares no dependency the operator does not have.
- **`resolve`** — `ManifestFile load:` → `source snapshot` → `Resolver`. A `Resolution` is written to `parley.lock` via the settled `IndexEntryWriter writeLock:on:` (byte-stable) and reported, exit `0`: one `<name> <version>` line per pin, or — when the project declares **no dependencies** — one pinned confirmation line. Zero pins used to mean zero lines, so a successful `resolve` printed nothing at all and read as a verb that had done nothing, on exactly the first run after `init`. Silence is the wrong report for success. A `ConflictReport` answers its narration lines, exit `1` — a conflict is a value, never an exception.

  **`resolve` runs without a source, and the index requirement is the manifest's, diagnosed inside the verb** (Sprint 21, §8 decision 83). The three manifest states are ruled together: **no dependencies** — resolves, writes the lock, answers the settled confirmation line, closing the first-session defect where `parley init` then `parley resolve` failed by grammar rather than by need; **only path dependencies** — resolves over the overlay alone (Doc C §1.3, no base source wired); **any index-needing dependency with no source wired** — one declared refusal at exit `1` on decision 80's precedent, naming what the manifest declares and the flags or `parley.config.st` that can answer, never the usage block, and writing nothing. A malformed `Package.st` under a flagless `resolve` answers the authoring diagnosis — the command was legal and the manifest is what is broken.

  **`check`, `tree` and `why` answer the same three states** (Sprint 21, §8 decision 84). A dependency-free or path-only project inspects flagless: `tree` renders the pins, `check` verifies them, `why` names the chain hop, all over the overlay composition or over nothing at all, and none of them touches an index because none is needed. An **index-needing** dependency with no source wired answers the *same declared refusal* `resolve` answers — exit `1`, naming what the manifest declares and the flags or `parley.config.st` that can answer, **never the usage block** — so the three verbs and `resolve` share one sentence rather than composing four. The lock boundary is reached where it always was: a `check` or `tree` over an unreadable or malformed `parley.lock` answers the §4.1 boundary diagnosis, which is what those verbs were always going to do once the grammar stopped intercepting them. The **write** verbs keep the grammar, so a source-less `install` still answers the `#needsIndex` usage error at exit `2` — the bound decision 83 named, still held by law. **When the manifest declares path dependencies, the snapshot is the overlay composition** (Doc C §2): a path dependency always wins over an index release of the same name, the lock records the pin's provenance in the `#path` tuple (Doc B §5.3), and a conflict in which an overlaid name participates carries one line naming the path provenance above the settled narration — the held-pins-line placement (§8 decision 46's family), because the resolver answers truthfully about the world it was given and cannot know a directory supplied it.
- **`install`** — the lockfile fast path, then the Sprint 5 pipeline, then registration:
  1. **Pin fast path:** if `parley.lock` exists, read it (settled reader), rebuild the `Resolution` (`fromLockEntry:`), and check `PinVerification of: manifest lock: resolution`. **The read is a boundary** (Sprint 9): a lockfile that does not parse, or parses but is not a `#'parley-lock' 1` artifact, signals one **`LockError`** naming the lock path and the reader's own message (wording pinned in RED) — never a raw `IndexEntryParseError`/`IndexEntryFormatError`, which is how a corrupt lock used to reach the §4.2 boundary undiagnosed and be answered with exit `70`. The diagnosis names **`parley update`** as the repair, because `update` is the one verb that ignores the lock entirely and rewrites it — the same shape as `init` in the missing-`Package.st` diagnosis (§8 decision 31). A corrupt lock is the operator's file, not Parley's defect.

     **Readability is checked before shape** (§8 decision 56, Sprint 16). The boundary above validates what the file *says*; it presumed the path could be read at all. `File>>exists` answers `true` for a **directory**, and `File>>contents` on one signals a kernel `SystemExceptions.WrongClass` that escapes the handler above — so a `parley.lock` that is a directory (a botched checkout, a volume mount, a stray `mkdir`) reached §4.2 as `internal error: WrongClass: Invalid argument -9223372036854771711: must be a SmallInteger - this is a defect in Parley, not in your project`: exit `70`, a kernel integer on screen, and the file never named. So the boundary now begins by requiring the lock path to be a **regular readable file**, answering one `LockError` naming it in the same three-part shape (path, defect, repair) when it is not. **The repair it names is not `parley update`** (ruled by the operator at the Sprint 16 RED review, amending this paragraph and §8 decision 56 as staged). The corrupt-lock repair names `update` because that advice is true *by construction* — `update` is the one verb that never **reads** the lock, so it can always rewrite one — and a directory-shaped lock is precisely the state that breaks the construction: `update`'s **write** cannot succeed either, which is why decision 56 refuses it along with every other verb. Naming it would answer the defect with the verb that answers the same refusal — a remedy that loops back to its own diagnosis, and §8 decision 58's standard broken by the sentence next door to it in the sprint that introduced the standard. The readability defect therefore names the two-step repair that works, and its second half is the settled *missing*-lock repair: once the path is removed the lock is **missing**, not corrupt, and `resolve` is the verb that writes a first one. **The settled corrupt-lock behaviour is unchanged and is the line that separates the two cases:** a lock that is *readable but malformed* is still ignored by `resolve`, which stays exit `0` (§4.1), because `resolve` is about to overwrite it. A lock that cannot be read as a file at all is refused by **every** verb including `resolve`, because the write that would fix it cannot succeed either — and answering `0` while being unable to produce a lock is the fail-wrong this whole boundary exists to prevent.

     **Writability is checked before the write, and it is the same rule** (§8 decision 59, Sprint 17). Decision 56 governs a boundary that *reads*; every boundary that *writes* owed the same diagnosis and did not have it. Probed through the shipped binary at the Sprint 16 close-out: a read-only `parley.lock` under `resolve`, a read-only project directory under `resolve`, a read-only `Package.st` under `add`, `init` into a read-only directory and `publish` into a read-only destination each answered `internal error: … - this is a defect in Parley, not in your project` at exit `70`, and **three of them never named the offending path**. A read-only checkout is an operator state, not a Parley defect. So **a boundary that writes a file requires that path to be writable before it commits to any part of the write**, answering one line naming the path and a remedy at exit `1`, and leaving the filesystem exactly as it found it — the rule `publish` already follows (Doc F §1) and the rule Sprint 16 applied to state directories. **Two predicates, because the toolchain forces two** (probed, 3.2.5): overwriting an existing file requires `isFile and: [isWriteable]`; creating a new one requires its *parent directory* to satisfy `isDirectory and: [isWriteable]`, because **`isWriteable` answers `false` for a path that does not exist** exactly as `isFile` does — absence is not unwritability, and a single-predicate check would turn every first `resolve` into a permissions error. Note the spelling: 3.2.5 has **`isWriteable`**, not `isWritable`.

     **The write boundaries, named.** Four *verbs* commit to a write, and each owes the check **before any part of that write is attempted**: **`resolve` and `update` writing `parley.lock`** — the *overwrite* predicate when a lock is already there, the *create* predicate when it is not, which is why an absent lock in a writable directory must keep resolving at exit `0`; **`add` rewriting `Package.st`** — overwrite, and the refusal leaves `parley.lock` byte-identical, because `add` is atomic across the pair (Doc B §2.1); **`init` writing `Package.st`** — create, so the path checked is the *working directory*, not the file; and **`publish` writing its entry and archive** (Doc F §1). Each answers **one line naming the path and a remedy** in the settled `'<path>: ...'` grammar at **exit `1`**, and a refused write leaves the filesystem exactly as it found it.

     **Four verbs is not four write sites, and the difference is deliberate.** The list above enumerates the boundaries an *operator* reaches by running a verb — the ones whose diagnosis a user reads. Parley writes in other places too: `ContentStore` opens a write stream under `.parley/store` and creates its root, and the `--git`/`--index` caches create directories beneath `.parley/`. Those are **not** absent from the rule — every one of them is inside a census class routed through `PathGuard` (below), and each is a row of the boundary table like any other. What they are not is a *verb-level* boundary with its own remedy sentence, because an operator does not choose where the content store lives. **Read the four as the verb enumeration and the census as the I/O enumeration; the table is the join, and it is the table the law reads.**

     **The earliest write of all is the state root, and it answers `ExecutionError`** (§8 decision 72, Sprint 17). `CommandLine createStateDirectories` creates `<workdir>/.parley` and `<workdir>/.parley/packages` once a verb is known to run (decision 57), which makes it the **first** write every verb performs — so in a working directory the operator cannot write, it is what fails first, for `resolve`, `init` and everything else. It is a row of the table like any other: role *the wiring state directory*, direction **write**, declared error **`ExecutionError`**. That class is the **settled carrier** for a filesystem precondition in the `'<path>: …'` grammar — Sprint 16 gave it exactly that job for the `exec` script — and `.parley/packages` is `ExecutionScope`'s own target, so no settled class fits better and no new one is warranted. **The name is a carrier, not a claim**: an `init` refused in a read-only directory has nothing to do with executing anything, and the row must not be read as saying otherwise (decision 43's standard). What the operator sees is the same one line naming the directory with a remedy, at exit `1`, that every other write row answers.

     **That row named the parent, and naming the parent conflated two states** (§8 decision 74, Sprint 18 — method finding **F13**). The rule above is deliberate: an operator told `<workdir>/.parley` could not be written is reading a name Parley invented, so the row names the working directory the operator chose. It is right when the parent really is unwritable, and it is **false** when the path exists and is **not a directory** — a regular file at `<workdir>/.parley`, or at `<workdir>/.parley/packages` with `.parley` writable, answers `/…/f1: could not be written - check its permissions and try again` about a directory that `test -w` reports **writable**, with a remedy that cannot work. That is decision 58's standard broken by the newest row in the table. **So `ensureDirectory:` distinguishes the two states by predicate before it composes anything**, and the wrong-type state answers a line naming **the offending path itself** with a cause and a checked remedy — the shape the `parley.lock` row already carries (`not a regular readable file - remove it and run parley resolve to write a new one`). The parent-naming rule survives for the state it was written for.

     **And the law over that row drives the shape-space of a path, not two permission bits.** This is the portable half, and it is what makes F13 forced rather than recorded: Sprint 17's laws made the *error class* total through `PathGuard` while the hostile states they drove stayed a list of exactly two, `unreadable` and `unwritable`. A path is not two things. The state-root row is driven through **absent** (created, exit `0`), **already a directory** (accepted), **a regular file** (refused, naming that path), and **a wrong-type or unwritable parent** (refused, naming the parent) — and each answers its own declared sentence. A chokepoint's totality over error *classes* is not totality over input *states*, and the difference is where a confident false sentence lives.

     **They all route through one site, and that is what makes the rule total rather than enumerated** (§8 decision 59 as amended). `Parley.PathGuard` (`src/compat/`) is **the single site in Parley that performs file I/O**: it carries both predicates, the diagnosis composition *and* the error translation. It prechecks — so a refusal happens before anything is created, which is the atomicity `publish` and `add` need — and it wraps the primitive itself in a **broad catch that translates any error into the boundary's own declared error naming the path**. Broad is correct here and does not contradict §8 decision 52: that decision governs a catch that *defers* to another boundary and must therefore name that boundary's errors and no others, while this catch *owns* the diagnosis and the block it guards contains nothing but the operation. A precheck alone would enumerate the failure modes somebody thought of — the mistake one level down from the one this rule exists to correct — and it would not hold: writing a read-only file raises a catchable `SystemExceptions.FileError`, but **reading a directory raises `SystemExceptions.WrongClass` and escapes a `FileError` handler**, so enumerating error classes is the same trap as enumerating states. It lives in `src/compat/` because it is toolchain adaptation: 3.2.5's spelling, its absent-path semantics, and the traps both carry.

     **The boundaries are a declared table with a prohibition over it.** One row per file boundary in the tool, each naming its path role, its **direction** (read or write) and the declared error it must answer — a class-side declaration in the settled shape of `deserializationBoundaries` / `sourceFlags` / `publishLayouts`, so the drift law reads it the way the existing drift laws read theirs. The law is written as a **prohibition rather than an enumeration** — *nothing outside `PathGuard` performs direct `File` I/O* — which is a far smaller and more tractable textual claim than finding every sender of a selector, and it is what finally makes relational-inventory row 21 forced. **The prohibition's exemption list is derived from a census of the property it prohibits, never from the set of sites that motivated the rule** (§8 decision 60): the eight classes doing direct `File`/`FileStream`/`Directory` I/O — `CLI`, `Publisher`, `SparseIndexSource`, `ContentStore`, `ManifestFile`, `DirectorySource`, `GitIndexSource`, `CommandLine` — each bounded to routing its I/O through `PathGuard` and adding its diagnosis, never changing what the verb does when the path is fine. A ninth class performing direct `File` I/O fails the law, and narrowing it to *"no I/O outside `PathGuard` at a declared boundary row"* is the disqualified implementation: it would still pass, and it would restore the enumeration the table exists to abolish.

     **The structural guarantee is about the row's SENTENCE, not about the whole line** (§8 decision 73, Sprint 17). Every row's diagnosis **opens with its path, states a cause in plain words, and — for a write row — offers a remedy that has been checked** (decision 58's standard, made a law). The law asserts that the operator's line **ends with the row's declared sentence** and that the sentence **opens with the path**. For eleven of the twelve rows the sentence *is* the line and the two readings coincide. The twelfth crosses a settled batching carrier: the only verb that reads a `.star` is `install`, and `Installer` composes `'<name> <version>: fetch failed - ', e messageText`, so the operator sees `a 1.0.0: fetch failed - Source directory has 1 problem(s): a-1.0.0.star: missing or unreadable archive file`. That carrier and that batch wrapper are settled and law-pinned for the *absent*-archive case, and routing the *unreadable* case into the same path is what `missing or unreadable archive file` has always promised — making the two answer differently would be the regression. **What bounds the prefix is stated rather than assumed** (decision 43): the same twelve rows are driven by the table law under both hostile states, and every one of them is held to *never* exit `70`, name a kernel class, print a backtrace, or carry the undiagnosed prefix. The prefix a carrier may add is bounded by that, not by the structural law's silence.

     **Sprint 19 adds the thirteenth row, and it arrives with the table's full discipline** (§8 decision 65). Role *`parley.config.st` (read)*, direction **read**, declared error **`ExecutionError`**, `#guarded` — decision 72's precedent applied a second time: `ExecutionError` is the composition root's settled carrier for a filesystem precondition in the `'<path>: …'` grammar, and **the name is a carrier, not a claim**. The alternatives fail on their own stated grounds: `SourceError` batches for a project (decision 44) where a config is one file with one defect, and `LockError`'s checked remedy names `parley update`, which cannot repair a config. The row's declared sentence follows decision 73's shape — opens with the path, states the cause, offers a checked remedy at exit `1` — and the four hostile shapes decision 65 names (not a regular readable file, does not parse, wrong tag, malformed body — the last including the two-source defect, Doc B §5.7) each answer it. The read routes through `PathGuard`, so the decision-60 census stays at eight; the tag joins `IndexEntryReader class >> formatTags` and its pinned rejection sentence (the Sprint 10 / Sprint 14 precedent — a declared exception, never a silent widening); and the read joins `deserializationBoundaries` as the fifth declared sender (§4.2), so both drift laws see it.

     **Sprint 18 extends the reach of that bound without amending the ruling** (§8 decision 62; §3.1). Decision 73 bounds what may prefix a row's sentence *inside the line the operator is shown* — and it measures the bound on the `CliResult`'s composed lines, because in Sprint 17 that was the whole of what reached the terminal. It is not: the authoring boundary executes the author's program, and the toolchain writes to the terminal by a route no `CliResult` law can see. So the marker-absence half of the bound — *never a backtrace, never a kernel class, never Parley's own source paths* — is re-asserted over **captured stdout and stderr from the shipped binary**. **Decision 73 stands unchanged and is not amended:** the claim it makes is the same claim, checked on a wider instrument, and the two do not govern the same territory twice. Where the two could be read as competing, 73 governs *the composition of a diagnosis line* and 62 governs *what may reach the terminal at all*.

     **This is a precheck, not a lock, and the docs say so** (decision 43's standard). A path can become unwritable between the check and the write, and Parley makes **no claim** about that window: the guard is a precheck, not a lock, and the tool does not claim otherwise. The check exists to turn the common case — a checkout the operator cannot write — into a diagnosis that names the file, and the write path keeps its existing failure behaviour for the racing case. Claiming atomicity here would be a promise the filesystem does not let this tool keep. **What the tool does claim is the narrower thing the translation buys, and it is stated rather than implied:** if the window is hit — or if any other unforeseen mode fails, a read-only mount, a full disk, an immutable flag — the caller still receives the boundary's own declared error naming the path, at exit `1`, and never the exit-`70` sentence claiming a defect in Parley. So the TOCTOU window can still *occur*; what it can no longer do is produce a bad diagnosis.

**The third rejection ground — body-shape validation (Sprint 10, closing §8 decision 35).** The two grounds above are *syntactic*. A lockfile that parses, carries `#'parley-lock'` and declares a supported format version but has a **malformed body** — a missing `#packages` key, say — passed both and reached `Resolution fromLockEntry:`, where it died as a *kernel* `SystemExceptions.NotFound` and was answered with exit `70`: "this is a defect in Parley, not in your project." The same sentence, on the same file, that this section exists to abolish, one hand-edit away. The §4.2 closed-set law was structurally blind to it, because that law enumerates **`Parley` error classes** and this one is the kernel's.

So after the tag and format-version checks, and **before** `Resolution fromLockEntry:` sees the value, the parsed structure must have the Doc B §5.3 shape:

- the two keys `#root #packages`, present, **in that fixed order** (§5.4 rule 2), `#root` a String;
- `#packages` an Array, each element a **four-element** `#(<name> <version> #sha256 <hex>)` — name and version Strings, the literal symbol `#sha256` in third position, the digest a String;
- each `#version` must **parse** as a `Version` through the settled `Version fromString:` — the Doc F §4.1 lesson, that a shape check never asks whether the string means anything;
- each `#sha256` must be **64 lowercase hex characters, or `''`** (Sprint 11, §8 decision 42; Doc B §5.3) — the shape a digest renders as, or the writer's own rendering of a pin with no published archive. Shape only: whether a digest matches its bytes stays `verifyHash:`.

A violation is one `LockError` problem naming the lock path, the defect, and `parley update` (wordings pinned in RED) — the same three-part shape the syntactic grounds already use. **One problem per lockfile**, first defect found: the operator is repairing one file, not auditing it, and the repair is the same regardless. Where a lock offends two value grounds at once, **every version is checked before any digest is**: the version wording is the older pinned answer, and a ground added later must not shadow one already settled. The settled `Version fromString:` is *consumed*, never re-implemented — it stays the single definition of what parses (Doc F §4.1).

`Resolution fromLockEntry:` is unchanged and stays trusting: it is fed only values this boundary has already accepted, exactly as `LibraryManifest fromIndexEntry:` is fed only entries the scan validated. Valid ⇒ that resolution is used **without consuming the source's snapshot** (mechanically provable: a snapshot-signaling source double). Invalid or absent ⇒ resolve fresh and rewrite the lock.
  2. **Hash-vs-cache:** for every pinned sha256 the store contains, `verifyHash:` must answer `true`. A tampered entry is a **fail-stop corruption report** naming the hash (exact wording pinned in RED), exit `1` — the store never repairs itself (Doc D §3: detection only; repair is an operator action).
  3. **Install:** `Installer install:` (cache hits skip fetch; an `InstallError`'s problems become the lines, exit `1`).
  4. **Register:** `ExecutionScope register` over the installed set (an `ExecutionError`'s message becomes the lines, exit `1`). Exit `0` on success.

     **A `#path` pin is no-fetch, no-store, no-register** (Sprint 21, §8 decision 69). The `CLI` hands the `Installer` the **path-free view** of the resolution, so a path pin never enters the Doc D pipeline and decision 25's empty-sha256 diagnosis keeps governing exactly the index pins it was written about — the two states answer differently because they are different: `''` records an index release that published no archive; `#path` records a pin no index supplied. Path-supplied code reaches the child at `exec` time instead (below). **`PinVerification` extends over all three declared kinds** (Doc B §2): a `devDependency:` missing from the lock is the settled missing-pin problem, and a path dependency verifies by **presence alone** — provenance is the *ground* for that, not a second check: its version is the sibling's declaration rather than a constraint of the root's, so there is nothing to compare and no constraint check to fail. **The sentence is tightened here (Sprint 21, ruled mid-sprint 2026-08-13) because it could be read as demanding a provenance check, and that reading is wrong twice over**: `PinVerification` verifies the **declared manifest** against the lock, so it learns a dependency is a path dependency from the *declaration* and never from lock-side provenance — asking it to read provenance would make it a consumer of the lock's own record, which is the boundary the composed resolution view is pinned against — and S12 builds a valid path pin through the settled `root:triples:` with no provenance at all. Whether a pin has *drifted* is `check`'s drift leg, which reads the sibling; verification is a function of two values and reads nothing.
- **`update`** — ignores any existing lock: resolve fresh, rewrite `parley.lock`, then install + register as above. (`install` keeps a valid pin; `update` is the verb that moves it.)
- **`update <pkg>`** (Sprint 12) — moves **one** package and leaves the rest of the lock where it is. The all-or-nothing grammar above is the honest MVP default and the wrong tool for the commonest real request: *take the patch release of this one dependency, change nothing else.* Today the only answer is `update`, which moves everything and hands the operator a diff they did not ask for and must review anyway.

  It resolves the ordinary way against a **narrowed snapshot** (Doc C §2.2): every *other* pinned package is held at its locked version, the named one is free to move, and whatever the named one drags with it moves too. The `Resolver` is untouched — a selective update is a normal resolution of a smaller world. On success the lock is rewritten byte-stably and `install` + `register` run exactly as `update` does; pins that did not move are byte-identical, which is the property that makes the diff reviewable and is worth a law of its own.

  Its diagnoses, all exit `1` and none of them exit `70`:

  - **no lock** — the same line the inspection verbs answer (`parley.lock is missing - run parley resolve to write it`). There is nothing to hold selectively when nothing is pinned.
  - **`<pkg>` is not pinned** — one line naming it, the `why` precedent: the operator asked about a package they do not have.
  - **held pins make it unmovable** — the settled `ConflictReport` narration, **preceded by one line** naming that the other pins were held and that `parley update` moves everything. The resolver answers truthfully about a world with few candidates but cannot know *why* the world was small; the verb had that context and owes the sentence (Doc C §2.2).

  When the named package is already at the newest version its constraints allow, that is a **success with a line saying so**, exit `0`, and the lock is rewritten to identical bytes — the `resolve`-with-no-dependencies precedent: a verb that prints nothing reads as a verb that did nothing. **Install and register still run** (ruled at the Sprint 12 close-out, §8 decision 48): already-newest changes what the verb *reports*, never what it *does*. The pins are unchanged, but nothing guarantees the store and the target directory still hold them — a cleared store or a fresh checkout is the ordinary case — and a verb that skipped the pipeline would answer `0` while registering nothing. `install` is idempotent, so running it unconditionally costs a cache-hit pass and keeps the verb's one contract whole.
- **`add <pkg> <constraint>`** (Sprint 13) — declares a new dependency in `Package.st` and moves the project to it in one operation. The edit is a **textual insertion into a recognized cascade, verified by re-loading through `ManifestFile load:`, and rolled back on any refusal** — the mechanism and its reasoning are Doc B §2.1, and the short version is that `Package.st` is executable Smalltalk the author owns, so Parley never re-renders it.

  After the edit it resolves against a snapshot narrowed to **hold every existing pin** (Doc C §2.2 — the third application of the trick, after retirement and selective `update`): adding a dependency should not silently move the ones already there, for the same reason `update <pkg>` does not. Then the lock is rewritten byte-stably and `install` + `register` run exactly as `update` does.

  **`add` is atomic** (Doc B §2.1): the manifest and the lock move together, or neither moves. Every diagnosis below restores the original `Package.st` byte-for-byte and leaves the lock as it stood. A fetched archive may remain in the content-addressed store, inert until a lock pins it — Doc B §2.1 states why that is outside the claim rather than an exception to it.

  Its diagnoses, all exit `1` and none of them exit `70`:

  - **no `Package.st`** — the settled missing-manifest line naming `parley init` (§8 decision 31); there is nothing to add to.
  - **a shape `add` cannot recognize** — one line naming the exact `dependency:constraint:` text to paste and the file, because a refusal that does not say what to type is a refusal that wastes the operator's time.
  - **already declared, with a different constraint** — one line naming the existing constraint. Changing a constraint is an *edit*, not an add, and a verb that silently overwrote one would be a different verb wearing this name.
  - **the new dependency is unsatisfiable while the existing pins are held** — the settled `ConflictReport` narration preceded by the held-pins line, exactly as `update <pkg>` answers it (Doc C §2.2). **The held-pins line is asserted only when holding is actually the reason** (§8 decision 58, Sprint 16): before emitting it, the verb re-resolves the same manifest against the **unheld** snapshot, and emits the line only if that resolution *succeeds*. When it fails too, holding was never the cause — the constraint is unsatisfiable outright — and the plain `ConflictReport` is answered alone. Without the check the line is a guess that reads as a finding, and it leads with `run parley update to move everything` on the commonest error there is, a typo'd package name, where `parley update` cannot help.

  **Already declared with the identical constraint is a success with a line saying so**, exit `0`, the file and lock byte-identical — the `update <pkg>` already-newest precedent, and idempotence is the property that makes `add` safe to put in a script.
- **`exec <script>`** — `ExecutionScope run:` with the script; `CliResult` carries the child's exit code and no lines of its own (the child already streamed to the terminal).

  **A `#path` pin's sources ride the composed child line, read fresh at exec time** (Sprint 21, §8 decision 68). For each `#path` pin in the lock, `exec` reads the sibling's manifest through the settled `ManifestFile` — at exec time, never from a cache — and the composed child invocation files in the sibling's `fileIns` in dependency order ahead of the script, which is what makes the workflow real: edit the sibling, re-run `exec`, no publish. The ruled-out alternative (rebuild and re-register the sibling's star per run) and its grounds are decision 68's. A sibling that is missing, unreadable or malformed at exec time answers its boundary's own diagnosis naming the sibling's path, exit `1`, spawning nothing.

  **The script is a precondition Parley checks itself, before any process is spawned** (§8 decision 56, Sprint 16). If `<script>` is not an existing *regular readable file* — absent, or a directory — the verb answers **one line naming it, exit `1`**, in the settled `'<path>: ...'` grammar every other missing-file diagnosis uses, and **spawns nothing**. This is not a retreat from §8 decision 45, which stands unchanged: the child's exit code remains a faithful pass-through, and Parley still never claims to know whether a script that *ran* succeeded. It is the boundary before that one. The distinction is what makes it necessary rather than merely tidy: decision 45's documented consumer constraint — a script whose success matters ends with an explicit `ObjectMemory quit:` — is **unavailable precisely here**, because a file that does not exist cannot carry a guard, so without this check there is no discipline an operator could adopt to make `parley exec typo.st` fail. On this toolchain it answers exit `0` and prints `gst: Couldn't open file`, and a directory argument answers exit `0` silently.

#### The inspection verbs (Sprint 11)

Three verbs that **read and explain, never change anything**. All three load the manifest, read `parley.lock` through the §4.1 validated boundary, and take the source's snapshot — they are allowed to consult the index precisely because none of them is `install`, whose fast path is law-bound not to (§8 decision 37). None writes a file, spawns a process, or mutates the store.

- **`why <pkg>`** — the dependent chains that put `<pkg>` in the lock. Renders one line per chain, root first, arrow-joined, each hop naming the constraint that demanded the next: a package pinned only because the root asked for it renders one short chain; a diamond renders two. A package not in the lock is a one-line diagnosis at exit `1` naming it (it is the operator's question about a package they do not have, not a defect). Chains are rendered in sorted order so the output is byte-stable.
- **`tree`** — the pinned graph root-down, one line per node, two-space indent per level, each node `<name> <version>`. A package reached more than once is rendered at each site (the tree is a tree, not a DAG rendering) with repeats marked, so the output cannot mislead about depth. Byte-stable: children sorted by name.
- **`check`** — the verb spelling of the pin fast path, and **the place retirement finally reaches the operator** (§8 decision 37 named it). It reports, in order: whether `parley.lock` exists and validates; whether `PinVerification of: manifest lock: resolution` holds; and **which pinned releases the index now marks retired**, with the author's reason from the settled `retirementReasonFor:version:`. All good ⇒ one confirmation line, exit `0`. Anything wrong ⇒ the problems as lines, exit `1`. A retired pin is a **problem**, not a warning: `check` exists to be run in CI, and an exit code that ignores a retirement would make the verb useless for the one job it has.

**All three on a lockless project** answer the one line `parley.lock is missing - run parley resolve to write it`, exit `1`. The graph comes from the lock, so without a lock there is nothing to inspect, and the repair for *absence* is `resolve` — the verb that writes a first lock — not `update`, which is the repair for a lock that exists and is *corrupt* (§4.1 above, and the `init` shape of §8 decision 31).

**`check` batches; the lock boundary does not (§8 decision 44).** `check` answers *every* problem it finds — the `PinVerification` problems first, then one line per retired pin in pinned-name order — where the lock read answers only its first defect. The two are not inconsistent: the lock boundary reports on one file the operator is about to repair by hand, and the repair is the same whichever defect is named first, while `check` reports on the *state of a project* for CI, where a first-problem-only answer would hide the rest and turn one red build into three.

**Where the graph comes from (§8 decision 40).** `why` and `tree` walk the **lock plus the snapshot**, never the `ConstraintLedger`. The ledger is transient — discarded when the search answers — and `Resolution` carries only the root name and `(version, sha256)` triples. Re-resolving to rebuild provenance would explain a world the operator is not running, since a fresh resolution may legitimately pick a different set than the lock pins. The edges come from the settled `IndexSnapshot>>dependenciesOf:version:`; the root's own edges come from its manifest. No resolver change, no new resolver state.

#### The verbs that close the grammar (Sprint 20)

Four verbs present in all seven of the package managers this project benchmarks against, and absent here. **None is new machinery:** `remove` is decision 49's recognizer applied to deletion, `info` and `search` read what the source layer already answers, and `outdated` compares the lock against the snapshot. **None of them enters the resolver** — decision 40's rule extended to all four, proved by a trap double on the real path exactly as Sprint 11 proved it for `why`/`tree`/`check`.

- **`remove <pkg>`** (§8 decision **67**) — deletes one dependency clause from `Package.st` and moves the project off it in one operation. The mechanism is Doc B §2.1's, applied to deletion: recognize the clause **and the separator that binds it to its neighbours**, delete exactly that span, preserve every other byte, verify by re-loading through the settled `ManifestFile load:`, restore the original bytes on any disagreement. It re-resolves **holding the remaining pins** (Doc C §2.2, the fourth application) — removing one dependency must not silently move the others — and it is **atomic across the manifest and the lock**, with the store outside the claim for the reason decision 49 records. Its diagnoses, all exit `1`: **no `Package.st`** (the settled missing-manifest line naming `parley init`); **a shape it cannot recognize** — one line naming the exact text to delete, **the file byte-identical**; **`<pkg>` is not declared** — one line naming it, the `why` precedent, and nothing written. Removing the **only** dependency is ordinary success: what remains is a valid manifest that re-loads, and the lock is rewritten with no pins.
- **`search <term>`** (§8 decision **80**) — substring match over the package names the index publishes, one line per hit (`name  latest-version  summary`), sorted, exit `0`. **No match is an answer, not an error:** one line naming the term and the index, at **exit `0`** — decision 57's rule that a question is not an error, and the behaviour of every benchmarked manager's own `search`. **It refuses over `--index`**, at exit `1`, naming the transport and the flags that can answer: a sparse index publishes one listing per package and no catalogue, and answering over the seeded closure would return the operator's own dependencies dressed as a complete result. The predicate keys off the source flag the wiring already holds (`CommandLine class >> sourceFlags`), never a new `PackageSource` selector.
- **`info <pkg>`** — one package's metadata: name, latest version, every published version **including retired ones marked as such**, summary, author, license, and dependencies. The metadata comes from the settled source protocol's **`manifestFor:version:`**, which answers a `LibraryManifest` carrying exactly these fields — *not* from the snapshot, whose release record is `{Version. sha256. dependencies}` and deliberately carries no metadata. The retirement reason comes from the settled `retirementReasonFor:version:`, which gains its **second** reader (the first is `check`, §8 decision 37). An unknown package is one line naming it and the index, exit `1` — the operator asserted a package exists and it does not, which is the `why` precedent and the opposite case from `search`'s empty answer.
- **`outdated`** — for each lock pin, **two columns**: the highest non-retired version the snapshot publishes that the manifest's constraint **still allows**, and separately the highest it publishes at all. Conflating them would be a wrong claim — *"you can upgrade"* and *"you would have to widen your constraint"* are different facts with different actions — and a **retired** newer release is never offered as an upgrade in either column. A fully current project answers one line saying so at exit `0`, the `resolve`-with-no-dependencies precedent. **A TRANSITIVE pin — one the lock carries and the root manifest never names — has no constraint of the operator's to report, so its allowed column renders a declared marker rather than a version** (§8 decision 82): letting "unconstrained" collapse into "the newest is allowed" would make the two columns coincide and recommend an upgrade the dependency graph may forbid, and omitting the pin would answer *"nothing is outdated"* over a lock carrying a stale release. The published column is reported unchanged, because that fact is true whoever owns the constraint.

**What the snapshot gains, and its exact bound** (Doc C §2): `IndexSnapshot` answers no enumeration of the names it holds, and `versionsOf:` **excludes retired releases by design** (§2.1). Both are needed here and neither existed, so the sealed value gains **two purely additive accessors** — a sorted enumeration of package names, and an all-versions-including-retired enumeration deliberately distinct from `versionsOf:`'s filtered view. No existing selector changes behaviour and the `Resolver` calls neither.

#### Dependencies you are developing (Sprint 21)

`dependency: 'name' path: '../dir'` and `devDependency: 'name' constraint: '…'` (Doc B §2, §8 decisions 68, 69) change what the snapshot may hold without changing any verb's grammar, and **every reporting verb's answer over a path-supplied name is ruled here, not improvised per verb** — the provenance split of Doc C §2 (resolution reads the overlay; reports read the index) decides all of them the same way:

- **`search`** enumerates index names only. A path-supplied name the index does not publish never appears — a path dependency is not published, and `search` reporting it would be the confident partial answer decision 80 exists to refuse, inverted.
- **`info <pkg>`** answers the index's publications. On a name supplied **only** by a path, it answers one ruled sentence naming the path provenance and that the index does not publish it, exit `1` — the settled unknown-package answer extended, never contradicted: the operator asked about the index, and the index's answer is still *no*, but a tool that knows why the project runs anyway owes that sentence.
- **`outdated`** renders a path pin's allowed column as a **second declared marker in decision 82's family** — one declared wording, consumed twice, naming the path. A path pin has no constraint of the operator's *and is not the transitive case*: the operator declared it, so the marker must not say the repair is out of their hands. The published column stays the index's answer, whoever overlays the name.
- **`why <pkg>`** names the declared directory in the chain hop, from the lock's own `#path` provenance (Doc B §5.3) — the operator asked why a pin exists, and *a directory you declared* is the answer.
- **`tree`** renders the pin as any pin, name and version — both are true, and depth is what `tree` reports.
- **`check`** verifies a path pin by **presence and by agreement with the sibling's current declaration**: a sibling that has moved its **declared version** since the lock was written is a problem naming `parley resolve`, because the lock is then a stale statement about the code `exec` actually loads. **The drift leg's bound is stated with the claim** (decision 43's standard): it compares the sibling's declared version — read through the settled `ManifestFile` — against the pin's recorded version, and **never file contents**; an edit that leaves the declared version alone is invisible to it, deliberately, because loading fresh content is `exec`'s job and diagnosing a stale *pin* is this one's. The division of labor is the retirement leg's own: `exec` loads the sibling fresh and never fails on drift; `check` is where drift becomes a diagnosis — as `install` proceeds and `check` reports. Its retirement leg passes path pins by — retirement is an index owner's assertion, and no index published the pin.

The two flags that join the grammar with this sprint — `--offline` and `--locked` — are §4.2's (mode flags, not source flags), and `resolve`'s source-optional grammar is §8 decision 83's, both above.

### 4.2 `CommandLine` — the wiring, as an object (Sprint 8)

The wrapper used to hold the wiring *and* the flag grammar *and* the error boundary, and was declared "glue, excluded from SUnit obligations". That declaration was wrong and it cost: the hardcoded file-in list silently missed `src/publish/`, so the shipped `publish` verb answered a `doesNotUnderstand:` backtrace — **and exited `0`**. Untested glue that decides an exit code is not glue; it is the product. Everything the wrapper did except loading, printing and exiting now lives in an object with laws.

- `CommandLine class >> in: aWorkingDir runner: aProcessRunner` — the working directory (`Package.st`, `parley.lock`, and the `.parley/` state beneath it) and the one process seam, held immutably. Construction is **pathname-passive**: no I/O, no process. Class-side construction; zero public setters; no value equality (the decision-23 precedent).
- `run: anArgvArray` — the whole wrapper's logic as a value-answering message: strip a leading `--`, parse the flag grammar out of the argv, wire the real collaborators, send `CLI run:`, and map anything that escapes to a diagnosis. Answers a **`CliResult`** — it never prints and never terminates the image.
  - **Flag grammar (MVP):** `--source <dir>` ⇒ a `DirectorySource` over `<dir>`; `--git <repo>` ⇒ a `GitIndexSource` over `<repo>` (Sprint 9); absent ⇒ `nil` (the verbs that need none still run). The two are **mutually exclusive** — both given is a usage error, exit `2`, because silently preferring one would make a typo look like a working command. The remaining arguments are the verb argv handed to `CLI run:` unchanged.
  - **The source flags are a declared table, not a chain** (Sprint 9): `CommandLine class >> sourceFlags` maps each flag to the source class it builds, and a **drift law** requires every `*Source` class shipped in `src/source/` to appear in it. Sprint 8's `bin/` drift law covers *directories*, and `GitIndexSource` proved a class can sit inside a named directory and still be unreachable because no flag builds it. Directories and flags are two different reachability questions and each needs its own law.
  - **The mode flags are a second declared table, and each is a guard invariant with one enforcement site** (Sprint 21, §8 decisions 68, 69, 83 — the two flags; the decision-81 idiom for their declaration). `--offline` and `--locked` are **valueless** — they build nothing and take no value, which is why they are not `sourceFlags` rows and must not be forced into that table's three-column shape — and they are extracted by the same flag parse that extracts the source flags, wherever they appear ahead of the verb argv. Each states an **invariant the invocation must hold**, enforced at the single site that could violate it, so no per-verb applicability table exists and a verb that cannot violate an invariant satisfies it trivially: **`--offline`** means *this invocation spawns no `git` and no `curl`* — enforced at source wiring, keyed off the settled `sourceFlags` exactly as decision 80's capability predicate is: a wired `--git` or `--index` source (from the argv or from `parley.config.st` alike) answers one declared line naming the transport the invocation wanted and that `--offline` forbids it, exit `1`, **spawning nothing** — while `--source` is unaffected, because a local directory is what offline means. **`--locked`** means *this invocation does not change `parley.lock`* — enforced at the one lock-write site: the verb computes what it would write, compares, and on any difference answers one declared line naming the **first differing pin** in sorted order, exit `1`, **writing nothing** — which composes with every verb that writes the lock, `add` and `remove` included (an `add` under `--locked` refuses with the manifest untouched, because the pair moves together or not at all, Doc B §2.1). A current lock under `--locked` is ordinary success. Both flags compose with each other and with any source flag; the question flags stay ahead of both, exactly as they stay ahead of the source flags (decision 57). Both sentences are **declared wordings consumed twice** (decision 81's rule). The usage block's header and `flags:` rows name both — a flag the help hides is a flag that does not exist.
  - **The configuration file records sources, and the mode flags deliberately have no config key** (Sprint 21). `--offline` and `--locked` are per-invocation assertions — a CI run's property, not a project's — so `#'parley-config' 1` (Doc B §5.7) is unchanged and byte-identical. A config key for either is deferred with a trigger: the first caller that genuinely cannot pass a flag.
  - **The configuration file supplies a default, never an override** (Sprint 19, §8 decision 64): when the argv carries no source flag, `run:` consults **`Parley.Configuration`** — which reads `<workdir>/parley.config.st` through the §4.1 boundary row (Doc B §5.7) and **answers values, deciding nothing** — and wires whichever single source the file declares, exactly as the equivalent flag would have. **An explicit flag always wins, and the config is then never consulted**, which is what keeps every settled law byte-identical. A file declaring more than one non-empty source is a malformed body (Doc B §5.7), refused at the read boundary rather than silently preferred — the same rule the flag grammar enforces one bullet up. Precedence lives here and nowhere else: the file is read by `Configuration`, the choice is made by `CommandLine`.

    **The file is consulted for every verb that runs, not only the verbs that need a source** (ruled at Sprint 19's close-out). The rule above says *when the argv carries no source flag*, and narrowing it to *and the verb consumes one* is a sentence this document does not contain. The consequence is stated rather than left to be discovered: in a project whose `parley.config.st` is malformed, **`init`, `check` and `tree` answer the config diagnosis at exit `1`** — the same one line naming the operator's own file with a remedy that works — instead of doing their work. That is decision 56's discipline applied consistently (every verb refuses an unreadable `parley.lock`, including the verbs that would not have read it), and the objection that `init` should be exempt has no instance: a directory already containing a `parley.config.st` is not a fresh project. **The two question flags stay ahead of all of it** — `--version`, `--help`, `-h` and the bare `help` are answered before the config is read and still exit `0` (decision 57), because asking a tool what it is must not depend on the state of a project. Probed through the shipped binary at the Sprint 19 close-out: `init`, `check` and `tree` exit `1` with the config line; `--version` and `--help` exit `0` unchanged.
  - **The two question flags — `--version` and `--help` — are answered ahead of verb dispatch and before any state directory is created** (§8 decision 57; `--version` Sprint 15, `--help` Sprint 16). Asking a tool what it is or how to use it is not running a command in a project: neither needs a working directory, and a `.parley/` created by a question is state created by a question. Both answer **exit `0`** — `--version` one line, `--help` the pinned usage block.

    **The question and the usage error share the block, not the answer** (§8 decision 79, Sprint 20). `helpResult` took `usageResult lines` **wholesale**, and that was recorded as a feature — *"the question and the usage error can never print two different texts"*. Once a usage error names what was wrong on line one (§4), the coupling becomes a defect rather than an economy: `--help` would inherit *"no verb given"*, which asserts a fault in a request that has none, and is the very thing decision 57 exists to prevent. So the **shared artifact is the block**: a usage error composes *reason line + block*, `--help` composes *the block alone*, and **neither is derived from the other's finished answer**. The single definition is preserved — both compose the same block, so the two can still never disagree about what the tool offers — while the false statement becomes unavailable. `--help`'s output is byte-identical to today's apart from its verbs row. `-h` and the bare verb `help` are accepted spellings of `--help`, because a user who guesses one of the three has asked the same question. **Exit `0` is the whole point of the ruling:** the usage text was already printed for `--help`, but at exit `2`, so the first command a new user types failed any `set -e` script or CI smoke check while `--version` beside it succeeded — the tool disagreeing with itself about whether a question is an error. **What stays exit `2` is unchanged and is the other half of the line:** `parley` with no argv at all, an unknown verb, and a *trailing* `--help`/`--version` on a verb (`resolve --help`) are all still usage errors, because failing to say what you want is an error even though asking for help is not. These are declared special cases recognized once, never a general "valueless flags are grammar now" change — the settled `valueOf:in:` trailing-flag behaviour is held unchanged by law.

    **No usage error creates project state either** (§8 decision 57, second half). The question flags are recognized before `createStateDirectories` for a stated reason — state created by a question is state created by a question — and the same reason covers every argv that never reaches a verb. As shipped it did not: `parley`, `parley nonsense` and `parley resolve` (no source) each created `<cwd>/.parley/packages` *before* answering the usage lines at exit `2`, so typing `parley` in any directory to see what it does left a directory behind. A command that refuses to run must leave the filesystem as it found it — the same rule `publish` already follows when it declines to create a destination it refuses (Doc F §1), and the same rule every refusal in this document follows. So **`createStateDirectories` runs only once a verb is going to run**: after the usage determination, never before it. This is discipline the tool already applies everywhere else, applied to its own state directory.

  **The usage determination lives in `CLI`, and `CommandLine` asks it** (§8 decision 57, site ruled by the operator at the Sprint 16 RED review). Whether an argv is going to run a verb depends on the verb list and on which verbs require a source — both `CLI` knowledge — so `CommandLine` cannot make the determination without restating a grammar that must have one definition. The dispatch's own "is this argv going to run a verb?" test is therefore extracted into **one predicate on `CLI` that `CLI>>run:` itself consumes**, and `CommandLine` asks that predicate before creating anything. Three constraints keep it one definition rather than a relocated copy: the dispatch is *expressed in terms of* the predicate, so no verb can be recognized by one and not the other; the predicate is a **function of argv alone** and touches no filesystem, because a determination that read files would be doing the verb's work before the verb; and `cliWithSourceIn:` stays *after* `createStateDirectories`, since the `--git` and `--index` builders create `.parley/git` and `.parley/index` and 3.2.5's `Directory create:` is not recursive. The two rejected alternatives are recorded in §8 decision 57.
  - **Wiring:** store at `<aWorkingDir>/.parley/store`, target at `<aWorkingDir>/.parley/packages` (created when absent), the git cache at `<aWorkingDir>/.parley/git/<sha256 of the repo location>` (Sprint 9 — the settled `Sha256` keys it, so any repo string becomes one deterministic filesystem-safe name and no escaping layer is invented), the injected runner. Deriving both from the working directory rather than the process's cwd is what makes the wiring law-testable under `tmp/`.

#### The diagnosis boundary

**No Parley command ever answers a backtrace, and no failing command ever exits `0`.** `run:` maps every outcome onto exactly three shapes:

| Outcome | `lines` | `exitCode` |
| --- | --- | --- |
| Success | the verb's own lines | `0` |
| Usage (unknown verb, wrong arity, source-requiring verb with no source) | **one line naming what was wrong**, then the pinned usage block (§8 decision 79) | `2` |
| A **diagnosed** problem — the verb answered it, or a declared Parley error reached the boundary | the problems / the message | `1` |
| An **undiagnosed** error — anything else reaching the boundary | one line naming the error's class and message text (wording pinned in RED) | `70` |

- The **declared Parley errors** are `ManifestError`, `SourceError`, `InstallError`, `ExecutionError`, `PublishError` and — from Sprint 9 — `LockError`. An error carrying `problems` contributes those as the lines; one carrying only a `messageText` contributes that as a single line. Exit `1` — the tool understood what went wrong and is telling the operator.
- Anything else is a **defect in Parley**, not in the operator's project: exit **`70`** (`EX_SOFTWARE`), distinct from `1` so a script can tell "your input is wrong" from "the tool is broken". Still one line, never a backtrace: Parley diagnoses, it does not dump.
- The boundary is a **closed set with a law**: every `Error` subclass defined in the `Parley` namespace is either mapped to exit `1` here, or is **declared undiagnosed with its ground named** — either *provably never signaled out of a verb*, or *reaching exit `70` by a named escape path that is accepted, for now, as fail-stop*. The two lists must partition the enumeration, so a new error class can never drift into the `70` bucket silently: the law fails first, and whoever adds the class must decide which list it belongs to and say why.

  **Sprint 9 restores the strong claim.** The two boundaries above — the lock read (§4.1) and the authoring file-in (§3) — remove all three named escapes, so from Sprint 9 every undiagnosed class is *provably never signaled out of a verb* and the weaker second ground has no members. It stays written down because the law must keep accepting it: the next error class to arrive may legitimately need it, and a partition rule that silently has only one branch is a rule nobody remembers is there.

  **What the closed set does not cover, and the law that covers it (§8 decision 35).** The claim, and the law that enforces it, quantify over `Error` subclasses **defined in the `Parley` namespace**. A *kernel* error raised inside a verb is outside the enumeration entirely, so it reaches exit `70` without any law noticing — which is exactly how the malformed-body `parley.lock` of §4.1 survived Sprint 9. "Every Parley error class is diagnosed or provably never signaled" is a strictly weaker statement than "every operator input is diagnosed", and the two must never be conflated. Enumerating more error classes does not close the distance: it could not have caught that bug and will not catch the next one.

#### The deserialization-boundary law (Sprint 10)

The invariant that carries the weight is **per boundary, not per class**: *every point where Parley reads a file the operator can edit validates shape before handing the value to a constructor, and answers a diagnosis at exit `1` on malformed content.*

Like Sprint 8's `bin/` directory law and Sprint 9's `sourceFlags` law, it needs its own enumeration rather than a widened neighbour. The anchor is mechanical: **`IndexEntryReader readFrom:` is the single literals-only parser**, so every sender of it in `src/` is a deserialization boundary by construction. `CommandLine class >> deserializationBoundaries` declares them, and the law reads `src/` and requires every sender to appear in the table — a new reader of an operator-editable file can never again ship without a diagnosis. The two senders today are the `CLI`'s `parley.lock` read (§4.1) and the `DirectorySource` scan (Doc F §4/§4.1); `ManifestFile load:`'s `Package.st` (§3) is the third boundary and is declared alongside them, because it reads an operator-editable file by a different mechanism (file-in, not the reader) and is exactly the kind of boundary a reader-anchored enumeration would otherwise miss.

The search runs over `codeOf:` the file — comments and string literals stripped — because Doc E anchors on *senders* and prose naming a send is not one (§8 decision 38), and over **whitespace-normalized** text from Sprint 11, so a receiver and selector split across lines are still one send (§8 decision 43). There is no reflective alternative on 3.2.5: `whichSelectorsReferTo:` searches literals rather than sends and finds none of the real senders, and `allCallsOn:` does not exist. The law's claim is therefore bounded and stated as bounded — *every textually spelled sender is declared* — with the indirect send answered by a convention (every sender spells its receiver) that the enumeration's pinned answer polices.

Each declared boundary owes one law: a malformed input reaches its verb and is answered at exit `1`, blaming nobody but the file. Together they are what lets Parley claim the sentence users actually rely on — *no operator file ever produces a backtrace, an exit `70`, or a lie about whose fault it is*.

  The weaker second ground was chosen at the Sprint 8 RED review over a claim the code could not support. Of the five currently undiagnosed classes, `ConstraintFormatError` and `VersionFormatError` meet the strong claim — every caller inside a verb catches them. Three do not, and their escape paths are declared rather than hidden: `IndexEntryParseError` and `IndexEntryFormatError` escape the `CLI`'s `parley.lock` read, and `ManifestVocabularyError` was declared to escape `ManifestFile load:` when the author's own `Package.st` has a typo. **The third declaration was factually wrong, and the Sprint 9 RED review corrected it** (§3): `ManifestVocabularyError` never escapes `load:` at all — the file-in swallows it, gst prints a backtrace, and `load:` answers a *different*, untrue diagnosis at exit `1`. The disease was worse than declared, not milder: not exit `70` blaming Parley, but a confident wrong sentence about the author's file, preceded by the backtrace this boundary exists to abolish. The two lock escapes are exactly as declared and do land on exit `70` — nonzero, one line, no backtrace — so for those the fail-stop invariant held and no script was lied to about success. What they lack is the *right blame*: they are the operator's problems reported as Parley's. Reclassifying them as exit-`1` diagnoses needs a lock-validation boundary and an authoring-error boundary, which is design and not a fix; it is a **ruled gap carried out of Sprint 8**, not a licence to leave the list vague.
- The mapping is expressed as **`on:do:` handlers**, never an `isKindOf:` chain. Smalltalk's exception system already *is* the taxonomy; re-implementing it as branching would be the kind-branching the architecture bans, and would silently mis-handle a subclass. `CommandLine` classifies by handling, and the one thing it decides is which of the four shapes above the outcome takes.

`CommandLine` is a **composition root**, not a manager: it holds no domain state, makes no domain decision, and answers a value. It exists because the wiring and the boundary are decisions — and decisions belong in objects with laws, not in a script nobody tests.

### 4.3 The executable wrapper (genuinely thin)

`bin/parley` (POSIX sh) locates the Parley checkout and execs `gst -f "$PARLEY_ROOT/bin/parley-main.st" -- <argv>`; `parley-main.st` lives in `bin/` — NOT `src/exec/`, whose every `.st` the test harness files in, and a main script executes on file-in. It does exactly four things and holds no logic:

1. file in **every** directory under `src/`, in load order;
2. send `CommandLine in: <cwd> runner: ProcessRunner new` `run: <argv>`;
3. print the result's lines;
4. `ObjectMemory quit:` the result's exit code.

Printing and exiting happen **here alone**, with exactly one declared exception: the location check below, which `bin/parley` must answer *before* `parley-main.st` can run at all. The file-in list stays explicit because load order is semantic, and it is **law-guarded**: a law reads the wrapper's own source and requires every existing `src/` subdirectory to appear in it, so a new `src/` directory can never again ship unreachable. (Per-invocation file-in is the honest MVP cost; a prebuilt image is deferred tooling polish.)

**The wrapper's location contract** (§8 decision 66, Sprint 17). `bin/parley` computed `PARLEY_ROOT` from `dirname "$0"` without resolving symlinks and **overwrote** any pre-set value, so the canonical installation — a symlink from a directory on `PATH` — pointed `PARLEY_ROOT` at the symlink's own directory and produced `gst: Couldn't open file '/home/user/.local/bin/parley-main.st'` **at exit `0`**: a total failure reported as success, on the first command a new user runs, in the tool whose headline guarantee is that no failing command exits `0`. Three obligations, and none of them is logic about a package:

1. **Resolve the symlink chain** before computing `PARLEY_ROOT` — including a symlink to a symlink, because one hop is not a contract.
2. **Honour a pre-set `PARLEY_ROOT`** rather than overwriting it. **This is a new obligation, not a settled one — stated precisely because the tempting justification for it is false.** The shipped-binary laws have composed `PARLEY_ROOT=<abs root> gst …` since Sprint 8, but they compose it around `gst` run *directly* on `bin/parley-main.st` (`CommandLineFixtures class >> shippedBinaryCommandIn:args:`), which never enters the wrapper; the only laws that invoke `bin/parley` itself go through `shellWrapperCommandIn:args:`, which sets no `PARLEY_ROOT` at all. So **nothing in the settled suite depends on this, and nothing in it would have noticed the wrapper overwriting the variable** — which is exactly why the behaviour needs a law rather than an assumption. What the obligation buys beyond correctness is that it makes the missing-script state constructible, and that is what makes obligation 3 testable at all.
3. **Check that `$PARLEY_ROOT/bin/parley-main.st` exists before exec'ing `gst`**, and when it does not, print one line naming that path and exit **`70`**.

**Exit `70` and not `1`:** a Parley installation missing its own main script is a defect in Parley, not in the operator's project, which is exactly what `70` means in the §4.2 taxonomy — and that taxonomy is otherwise untouched here. **The wrapper must check rather than delegate**, because delegation does not work on this toolchain: **`gst -f <missing file>` prints its own message and exits `0`** (probed, 3.2.5 — the same behaviour §8 decision 45 records for `exec`, reached here by the wrapper instead of by a verb). A wrapper that simply exec'd `gst` and passed its status through would therefore report every broken installation as a success.

This is Sprint 17's own subject rather than a neighbour of it — a filesystem state, the main script not being where the wrapper looked, answering the wrong exit code and naming nothing the user can act on (§8 decisions 59 and 66). The wrapper stays **glue with no logic**: finding itself is not a decision about a package, and it stays law-guarded exactly as the file-in list is.

## 5. SUnit Requirements for This Doc

- **`ProcessRunner`:** real execution laws — a command exiting `7` answers `7`; success answers `0`.
- **`ExecutionScope`:** the pinned child command composition (pure, exact string); `register` executes the real plan (real `gst-package`, real archive bytes land byte-identical in the target as `<name>.star`); fail-stop on the first failing command (real: staging copies garbage bytes fine, then `gst-package` exits `1` on the non-archive — the `ExecutionError` names that registration command and code; later commands never run); `run:` really launches the curated child (a script leaves a sentinel; the exit code comes back).
- **`ManifestFile`:** loading a written `Package.st` answers the built manifest (round-trips name/version/dependencies); a define-less file signals the pinned error; **an absent path signals the pinned one-problem `ManifestError` before any file-in is attempted** (Sprint 8) — observable at the boundary as exit `1`, never `70`; **a `Package.st` sending an out-of-vocabulary selector signals one `ManifestError` carrying the vocabulary error's message and suggestion** (Sprint 9), and the same input through the shipped binary exits `1` with no backtrace; **a `Package.st` whose declarations fail validation (e.g. `version: 'banana'`) signals the builder's own `ManifestError` with every problem in the batch preserved** (Sprint 9) — never the define-less diagnosis, and never a backtrace.
- **The lock boundary (Sprint 9):** an unparseable `parley.lock` and a wrong-tag `parley.lock` each signal one `LockError` naming the path and the reader's message, on `install` and on any verb that reads the lock; `update` is unaffected by a corrupt lock and repairs it (it never reads one); the diagnosis names `parley update`. Observable at the §4.2 boundary as exit `1`, never `70`.
- **Lock body-shape validation (Sprint 10):** each §4.1 shape violation — a missing key, keys out of the §5.4 order, a non-Array `#packages`, a package tuple of the wrong arity, a missing `#sha256` marker, a non-String field — signals one `LockError` naming the path and the defect, at exit `1`; an unparseable `#version` inside a shape-perfect lock does the same (the Doc F §4.1 lesson); a lock Parley itself wrote always passes, proved against the settled writer's own output rather than a hand-copied literal. `Resolution fromLockEntry:` is never reached with an unvalidated value.
